# v0.11 Devices and Nodes View Multistage SOP

Status: **Proposed / Stage 0 design package. Product code MUST NOT begin until
RFC-0018 and this SOP receive Architecture Review GO at Gate A.**

Authorization: `V11-CONSTRUCTION-20260929-A1`  
Controlling RFC: `docs/rfc/0018-devices-and-nodes-view.md`  
Baseline: `v0.10.0-rc.1` (`cc826b720124bd9249a334c6f1786e73bb44266b`)

## 1. Rules of Engagement

- Every stage ends with an **independent code review** (`@code-reviewer` /
  `@code-reviewer2`); the next stage MUST NOT begin until that review records
  an explicit PASS verdict. Review records live in `docs/review/` named
  `YYYY-MM-DD-v11-stageN-<gate>-<sha>.md`.
- Product code is written on stage branches
  (`chore/v011-stage<N>-<slug>`) descending from the governance root; docs
  commits may land on the design branch.
- The **candidate-freeze rule** applies exactly as in v0.9/v0.10: one frozen
  candidate per evidence round; once frozen, later phases produce only
  qualification/evidence; a real problem means a new candidate and fresh
  candidate-bound evidence.
- Evidence closures are **evidence-only commits** (direct children of the
  frozen candidate) and MUST NOT reference their own SHA.
- Mounted evidence must mask session IDs, operator principals, and any live
  values it records, and its sanitization statement must accurately describe
  what was masked (v0.10 Final Review P2 lesson).
- The selector-apex allowlist, the public/unauthenticated surface, and the
  v0.10 edge adjudication are **frozen boundaries** for every stage; a change
  to any of them is a stop-work event, not a fix.
- Tag/release creation, production promotion, and DNS cutover remain
  separately authorized actions throughout.

## 2. Acceptance Baseline

- Full suite green: `npm run check` (public-tree check + `node --test`),
  zero failures, before any stage gate; docs commits must pass the
  public-tree check too (no private-IP literals — examples use TEST-NET-1
  `192.0.2.10` — and no credential-like assignments).
- The M22 matrix (RFC-0018 §3 D7) is the canonical acceptance matrix for
  v0.11. Its 16 automated fields must be mechanically enforced
  (candidate-bound validation, `requirePass: true`); its 6 mounted fields
  must be executed live on the two-node deployment (one direct, one reverse)
  before closure. **M1 and M2 require a real phone** (physical device,
  narrow viewport), not an emulator-only run; M3 additionally spans a phone
  session and a desktop session.

## 3. Staged Implementation Plan (Stages 0 through 4)

### Stage 0: RFC-0018, Authorization & SOP Gate (Gate A)

Deliverables:

- `docs/rfc/0018-devices-and-nodes-view.md`;
- `docs/release-attestations/v0.11-construction-authorization-2026-09-29.json`
  and `.md`;
- this SOP.

Exit criteria:

- **Gate A Review**: independent architecture review of the design package —
  RFC invariants against the existing registry implementation (apex
  allowlist location and tuples, browser request admission chain, session
  store schema and lifecycle, selector read model, asset maps, flow
  tracker), scope discipline, threat model. Design claims must be verified
  against the real code (live `createHubServer` probes where practical),
  not taken from prose. **GO requires P0/P1/P2 = 0**; remaining P3s are
  converged before the next stage begins.

### Stage 1: Registry Session Surface & Selector Read-Model Enrichment (Gate 1)

Deliverables (in order; the first two are Gate 1's first review targets,
mirroring the v0.9/v0.10 precedent of shipping the mechanical harness with
the design):

- `scripts/v11-devices-nodes-acceptance-matrix.mjs` defining the M22 field
  set with the `assertM22MatrixShape` / `requirePass` / `scope` conventions
  of the v0.9–v0.10 matrix scripts, plus the governance-contract test
  (`test/v11-governance-contract.test.mjs`) wiring it into the suite and
  cross-referencing this SOP, the authorization JSON, and RFC-0018;
- `registry.listSessions()` and `registry.revokeSession({ sessionId, actor })`
  with the `session.revoke` audit row in one transaction (RFC-0005 D7
  pattern); no new columns in `browser_sessions`;
- `GET /hub/sessions` (read-only, trailing-slash variant included) and
  `POST /hub/sessions/revoke` (CSRF-gated) inside the existing
  `handleBrowserRequest` flow — admission, origin/`Sec-Fetch-Site`,
  session, CSRF, per-IP rate limit, single-target validation with
  `invalid-target-scope` rejection, `not-found` for unknown/revoked ids;
  response shapes per RFC-0018 D2 (never any `csrf_token` value);
- `route.activeFlows` added to `buildSelectorNodeRow` /
  `buildSelectorReadModel` from the existing `flowTracker`
  (`src/registry/selector-view.mjs`) — **zero** changes to the apex branch
  of `src/registry/server.mjs` (asserted by A3);
- mechanical tests for fields A1–A16 (A3 apex-allowlist regression and A14
  node-route passthrough explicitly included).

Exit criteria:

- **Gate 1 Review**: independent review of the registry/session changes with
  regression focus (A2, A3, A6, A7, A9, A14, A16).

### Stage 2: Selector & Management UI — Indicators, Target Scope, Devices View (Gate 2)

Deliverables:

- `ui/selector/view-model.mjs` + `index.html` + `app.mjs`: explicit
  `target:` authority line and `activeFlows` indicator per card (Open still
  navigates only to the server-provided `openUrl`); periodic polling refresh
  with the manual refresh retained and polling failure degrading to the
  existing error banner;
- `ui/selector/styles.css`: responsive breakpoints (narrow-viewport layout,
  touch-safe controls, no horizontal overflow at phone widths), no external
  URLs/fonts/frameworks;
- management surface (`ui/index.html` + `app.mjs` + `view-model.mjs`): the
  **Devices and Nodes** section — session list (hint-only rendering of
  session ids, last activity, revoked state), explicit revoke with
  confirmation, node rows with the same target/flow indicators unified in
  one screen;
- `docs/registry-ui.md`: the Devices and Nodes section documenting exactly
  what the hub shows (and its stated limitations — no device fingerprint, no
  node-local DSH session state);
- controller-level tests for the view-model functions (target/flow label
  contracts A11/A12; hint-only rendering assertion).

Exit criteria:

- **Gate 2 Review**: independent review of the client behavior; the DOM
  model assertions (A11, A12, A15) reviewed as tests, not prose.

### Stage 3: Regression, Hygiene & Boundary Sweep (Gate 3)

Deliverables:

- boundary regression pass: apex allowlist byte-identical (A3), node routes
  pure proxies (A14), cookie attributes unchanged on every issuing path
  (A16), `/hub/nodes` + `/hub/overview` shapes unchanged;
- session lifecycle sweep: bootstrap → activity → idle expiry → revocation
  → audit, including revoking-own-session and concurrent-session isolation
  (A7/A8/A9);
- secret-hygiene scans: no `csrf_token` value in any new response; no
  session id rendered into the DOM beyond the hint (A4 + Stage 2 tests);
- full `npm run check` green; public-tree check clean.

Exit criteria:

- **Gate 3 Review**: independent review; candidate freeze readiness.

### Stage 4: Candidate Freeze, Mounted Evidence & Closure (Gate C → Mounted → Final Review)

Deliverables (paths fixed so the evidence-only closure stays pure):

- **freeze record**: `docs/release-attestations/v0.11-candidate-freeze.md`
  declaring the frozen candidate SHA — a docs-only commit on the release
  branch; the commit that contains this record is itself the frozen
  candidate (v0.9/v0.10 precedent: the gate record commit is the freeze
  point);
- **fresh automated qualification report**:
  `docs/review/v11-m22-automated-qualification-<sha>.json` — a **direct
  child commit of the freeze commit**, generated by the candidate-bound
  report generator BEFORE the mounted run (shape-canonical; the full suite
  run is the real pass evidence). The evidence-only closure remains a
  separate, later commit containing only the attestation and
  `test/evidence/v11/**` — never the freeze record or the qualification
  report;
- mounted run on the real two-node deployment executing M1–M6 with sanitized
  bindings (candidate SHA, runId, node IDs, TLS/browser provenance), evidence
  under `test/evidence/v11/` with SHA-256/byte manifest; the run requires:
  one direct node and one reverse node, the v0.10 QR pairing flow to put a
  live session on a real phone, a second (desktop) session on the management
  origin, and node-A outage simulation for M5 — **no deployment-config
  changes** (edge, DNS, certificates) are part of this wave; any perceived
  need for one is a stop-work event;
- evidence-only closure commit (direct child of the frozen candidate):
  `docs/release-attestations/v0.11.0-rc.1.md` + `test/evidence/v11/**` only;
- **Final Review** (P0/P1/P2 = 0 required) closing v0.11 engineering
  acceptance.

Exit criteria:

- Final Review PASS recorded in `docs/review/`.

## 4. Stop-Work Triggers

In addition to the RFC-0018 §5 stop-work matrix: any evidence staleness,
provenance mismatch, sanitization-statement inaccuracy, cleanup residue, or
a review verdict below PASS stops the wave — a new candidate and fresh
evidence are required; no in-place patching of a frozen candidate.
