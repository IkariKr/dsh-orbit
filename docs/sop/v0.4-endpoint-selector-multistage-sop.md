# v0.4 Endpoint Selector Multistage SOP

Status: Proposed. Construction is **not authorized** until RFC-0010 / RFC-0011 and the v0.4 activation amendment to RFC-0008 pass architecture review.

This SOP intentionally keeps v0.4 small. It builds one safe browser entry point over multiple **server-reachable** DSH nodes. It does not anticipate every future DSH authentication model and it does not implement v0.5/v0.6 early.

## Scope of authority

Design authority for this construction:

- RFC-0001 node identity;
- RFC-0003 node authentication;
- RFC-0007 browser management authentication;
- RFC-0008 Hub service identity lifecycle plus its v0.4 activation profile;
- RFC-0009 capability/health semantics;
- RFC-0010 node endpoint and routing model;
- RFC-0011 browser node selection;
- ADR-0001 third-party plugin boundary.

The accepted v0.3 Registry is the baseline. Do not refactor it merely because v0.4 adds routing.

If implementation discovers that any of the following must change, STOP and request architecture review before continuing:

- node identity;
- public route-authority model;
- Hub -> Node credential direction;
- browser authentication/trust model;
- `web.routes` capability meaning;
- automatic failover policy;
- v0.4/v0.5 scope boundary;
- third-party plugin boundary.

## DSH evolution rule

DSH remains fast-moving. v0.4 must therefore keep DSH-specific compatibility at the node edge.

Do not encode in the Hub router or selector:

- DSH cookie names;
- launch-token/query parameter names;
- private RPC names beyond behavior-based smoke probes;
- frontend component structure;
- DSH package source matchers;
- third-party plugin paths or versions.

The Hub routes opaque HTTP/WebSocket traffic. The existing compatibility profile and `web.routes` evidence decide whether a specific DSH version is routable. If upstream changes authentication, fix or retire the node-local adapter; do not redesign the selector unless an Orbit-owned invariant actually changed.

## Forbidden scope (all stages)

- reverse connection, reverse tunnel, NAT traversal, or device pairing (v0.5);
- multiple route targets, route priorities, automatic endpoint discovery, or failover;
- path-prefix DSH routing;
- friendly DNS aliases or per-user aliases;
- one Orbit page concurrently controlling multiple DSH nodes (v0.6);
- cross-node session migration;
- fleet execution or broadcast actions (v0.7);
- general-purpose service-mesh/TCP-tunnel features;
- third-party plugin compatibility code;
- adding a DSH compatibility profile merely because a package builds.

## Global safety invariants

- `nodeId` is identity; route target/public route authority are mutable routing metadata.
- A node-supplied URL never becomes routable without operator approval.
- A public node route maps to exactly one node.
- A node route never automatically fails over to another node.
- Hub -> Node route credentials are per-node and never fleet-wide.
- Route-auth metadata is stripped before DSH.
- `registryContact` remains heartbeat-only; `reachable` becomes Hub-route-probe-only.
- `web.routes` must be fresh before Open is enabled.
- DSH stays the execution runtime; Orbit does not emulate DSH sessions/settings/agents.

# Stage 1: Route target persistence

**Objective**

Give each registered node zero or one operator-approved server-reachable route target without creating an unauthenticated Hub -> Node probe path. `reachable` remains `unknown` until Stage 2 activates the per-node Hub identity and route ingress.

**Implementation scope**

- Persist one route target per node.
- Browser management actions to set/remove the target with CSRF/operator attribution.
- Strict target validation: absolute origin, production HTTPS, no embedded credentials, no path/query/fragment.
- Audit route-target changes.
- Keep `reachable = unknown`; Stage 1 does not contact the route target as a trusted application probe.

**Required outputs**

- schema migration and backup/restore coverage;
- node detail/management API exposes route target state without exposing credentials;
- operator UI can configure/remove the target;
- no route probe, Hub identity, or public node proxy yet.

**Required automated tests**

- migration from the current v0.3 schema;
- malformed/credential-bearing targets denied;
- node cannot self-set the target through heartbeat/report;
- saving/removing a target leaves `reachable = unknown`;
- node A target changes never mutate node B.

**Required live evidence**

- two registered nodes with independently configured route targets retained across Hub restart.

**Forbidden scope**

- no routing browser traffic;
- no multiple targets/failover;
- no Hub route key yet.

**Failure / stop conditions**

- target validation permits arbitrary node-supplied SSRF targets;
- an unauthenticated route probe is introduced before Stage 2;
- target persistence mutates unrelated health dimensions.

**Stage completion criteria**

Route metadata is deterministic, persistent, independently tested, and migration-safe; no unauthenticated reachability path exists.

# Stage 2: Per-node Hub route identity activation

**Objective**

Activate RFC-0008 for the first real Hub -> Node use without introducing a fleet-wide secret or requiring inbound callback during provisioning.

**Implementation scope**

- Hub generates one Ed25519 route identity per node.
- Node receives Hub public material through the existing authenticated Node -> Hub control path as fixed by the RFC-0008 amendment.
- Node persists accepted Hub public material before acknowledging activation.
- Implement overlap rotation and immediate revocation on node deletion.
- Implement `ORBIT-ROUTE-V1` verification in a small node route-ingress component.
- Route ingress has an Orbit-owned authenticated readiness probe; it does not parse DSH APIs.
- Activate RFC-0009 `reachable`: default 60-second probe cadence, three consecutive failures -> `unreachable`, one authenticated success -> `ok`.

**Required outputs**

- per-node Hub key persistence and schema changes;
- node-side trusted Hub public-key persistence;
- route-ingress process/component with authenticated readiness;
- reachability transitions/events driven only by Hub route probes;
- audit/events for provision/active/rotation/revocation.

**Required automated tests**

- A Hub identity authenticates to A only;
- A identity fails on B;
- malformed/expired/replayed route proof fails before downstream;
- another public route authority fails even for the same node;
- node restart preserves trusted Hub public key;
- Hub restart preserves private key identity;
- rotation overlap accepts both keys, then old key fails;
- delete immediately revokes Hub-side route eligibility/signing; after the Node observes `401 revoked`, its persisted REVOKED state disables local route ingress acceptance;
- no route-auth header reaches the downstream fixture;
- probes never modify `registryContact`, compatibility, or capabilities;
- take A ingress down: after the fixed failure threshold A becomes `unreachable`, B stays `ok`; one authenticated A success restores `ok`.

**Required live evidence**

- two real Node processes accept only their own Hub route identity;
- both route targets reach `ok` independently;
- restart Hub and both Nodes without re-provisioning identities.

**Forbidden scope**

- no DSH browser proxy yet;
- no reverse-connected transport;
- no general-purpose tunnel protocol.

**Failure / stop conditions**

- any symmetric fleet-wide secret is introduced;
- Hub receives a node-local DSH/internal gateway secret;
- route authentication requires buffering arbitrary browser request bodies.

**Stage completion criteria**

Authenticated Hub -> Node route ingress and route-derived reachability exist for two nodes, and key lifecycle survives restart/rotation/revocation.

# Stage 3: Deterministic public route authority + HTTP proxy

**Objective**

Route normal HTTP traffic from a deterministic node subdomain to exactly one eligible node without path rewriting.

**Implementation scope**

- Configure selector authority and wildcard route domain.
- Parse only the RFC-0010 deterministic `n-<32hex>` host label.
- Resolve host -> exact `nodeId` -> eligibility -> route target.
- Sign each upstream request with `ORBIT-ROUTE-V1`.
- Route ingress verifies and forwards to the node-local DSH adapter.
- Preserve method, raw path/query, streaming request/response body, status and relevant headers.
- Return an Orbit-owned unavailable response for ineligible nodes.

**Required outputs**

- HTTP route proxy;
- deterministic host mapping tests;
- unavailable page/response with selector link;
- deployment example for wildcard DNS/TLS assumptions.

**Required automated tests**

- invalid/unknown node route host denied;
- route A can never resolve to B;
- query/path bytes used for signing match the forwarded raw target;
- DSH/root fixture sees no node path prefix;
- upstream 4xx/5xx is returned, not converted to another-node routing;
- `web.routes` absent/stale disables routing;
- deletion disables route immediately.

**Required live evidence**

- browser/fetch reaches static root/assets on two route authorities through the same Hub deployment.

**Forbidden scope**

- no WebSocket yet;
- no automatic retry to a different node;
- no DSH-specific auth manipulation in the Hub.

**Failure / stop conditions**

- proxy needs path-prefix rewrites;
- router must understand DSH cookie/token internals to identify a node;
- failed A route is served from B.

**Stage completion criteria**

HTTP traffic is host-routed, target-preserving, and DSH-opaque for two nodes.

---

# Stage 4: WebSocket and long-lived routed traffic

**Objective**

Make routed DSH WebSocket/long-lived traffic obey the same node authority and identity rules as HTTP.

**Implementation scope**

- Proxy WebSocket upgrade using the same host -> node resolution.
- Authenticate the upgrade with `ORBIT-ROUTE-V1`.
- After successful upgrade, stream frames transparently; do not inspect DSH frames.
- Existing connection remains bound to the node selected by its authority until close.
- Hub/Node restart may close connections; reconnect goes back to the same authority/node.

**Required outputs**

- WebSocket route proxy and route-ingress support;
- connection cleanup/resource limits;
- no cross-node retarget mechanism.

**Required automated tests**

- A WebSocket reaches A only;
- B route reaches B only;
- route proof required on upgrade;
- target loss closes/fails the A stream without connecting to B;
- Hub restart does not change authority-to-node mapping;
- proxy does not parse frame payloads.

**Required live evidence**

- long-lived DSH/browser transport works through both node authorities for the currently supported DSH profile.

**Forbidden scope**

- no multi-node multiplexing;
- no reverse tunnel;
- no cross-node reconnect.

**Failure / stop conditions**

- implementation requires interpreting DSH WebSocket messages;
- one connection can change target without a new browser navigation/authority.

**Stage completion criteria**

HTTP and WebSocket traffic share one deterministic route decision and fail closed.

# REVIEW GATE A: Routing core

Stop all construction after Stage 4.

Review must independently verify:

- node identity is not route identity;
- one operator-approved route target only;
- reachability separation;
- RFC-0008 per-node identity lifecycle;
- `ORBIT-ROUTE-V1` negative matrix;
- exact host-to-node mapping;
- no path-prefix rewrite;
- HTTP/WS transparency;
- no failover;
- no DSH-private assumptions in Hub routing code.

GO is required before Stage 5.

# Stage 5: Endpoint selector UI

**Objective**

Expose the v0.4 product experience: one familiar URL, explicit node selection, clear route eligibility.

**Implementation scope**

- selector page at the configured selector authority;
- rows from Hub Registry only;
- display name/node ID, versions, registry contact, reachable, compatibility, relevant capabilities;
- enable Open only when route eligibility passes;
- full navigation to deterministic node authority;
- concise unavailable reason;
- route target administration stays in node management/detail rather than becoming a topology editor.

**Required outputs**

- selector UI;
- direct selector link from node-unavailable response;
- accessibility/loading/empty/error states.

**Required automated tests**

- no fake client-side health derivation;
- two rows remain independently actionable;
- stale/missing `web.routes` disables Open;
- Open URL derived from node ID, never display name;
- direct bookmark route still passes server-side eligibility.

**Required live evidence**

- real browser opens selector, then Node A; second tab opens selector, then Node B; first tab remains A.

**Forbidden scope**

- no global active-node cookie/state;
- no embedded iframe multi-node view;
- no fleet dashboard expansion.

**Failure / stop conditions**

- two tabs can change each other's target without navigation;
- UI invents eligibility not enforced by the server.

**Stage completion criteria**

The selector answers only discovery, eligibility, explicit selection, and return/switch.

# Stage 6: Real two-node mounted E2E

**Objective**

Prove the complete v0.4 path against two real server-reachable DSH nodes.

**Implementation scope**

- one Hub/gateway candidate deployment on a **rehearsal selector + wildcard route domain** that is distinct from the production `dsh` authority;
- wildcard selector/route TLS;
- Node A and Node B with distinct route targets and Hub identities;
- currently supported DSH compatibility profile on both nodes;
- real HTTP root/assets/API, WebSocket/long-lived transport, existing-session smoke where applicable;
- route-target outage, node deletion, Hub restart, Node restart.

**Required outputs**

- sanitized evidence file/report with exact Orbit commit, DSH version/profile, node IDs, rehearsal route authorities, image/process identity, TLS verification state and test outcomes;
- no secrets, cookies, bearer values or private keys in evidence.

**Required automated tests**

- full repository `npm run check`;
- mounted drill contract tests.

**Required live evidence**

At minimum:

1. A and B both eligible;
2. selector opens A and B independently;
3. API/readiness/assets/WS pass for both;
4. A route outage -> A unavailable/unreachable, B unaffected;
5. A never fails over to B;
6. restore A -> A routable again;
7. delete A -> route denied immediately;
8. Hub and B remain healthy;
9. restart Hub/Nodes -> stable identities and deterministic route authorities remain.

**Forbidden scope**

- do not use a reverse connection to make the drill pass;
- do not add a second endpoint fallback.

**Failure / stop conditions**

- evidence uses synthetic-only DSH fixtures for the final route path;
- target identity cannot be proven from the evidence.

**Stage completion criteria**

The intended NAS + directly reachable workstation class of deployment works through one selector.

# Stage 7: Failure, restart and compatibility hardening

**Objective**

Harden only the failure modes discovered by the v0.4 design and mounted E2E. No new product capability.

**Implementation scope**

- schema migration/backup/restore with route/Hub-identity state;
- Hub/Node/gateway restart recovery;
- Hub route-key rotation and overlap;
- clock-skew/replay-cache behavior;
- TLS/certificate failure;
- stale compatibility and capability withdrawal;
- DSH process unavailable behind an otherwise reachable route ingress;
- browser direct bookmark after node delete/reenroll;
- resource cleanup for dropped HTTP/WS connections.

**Required outputs**

- deterministic failure drills;
- troubleshooting/operator docs.

**Required automated tests**

- migration from v0.3 current schema;
- real backup -> mutate route/key state -> restore;
- corrupted route/key persistence fails closed;
- route key rotation survives process restart;
- unsupported DSH version never becomes routable by version guess;
- DSH compatibility adapter failure withholds `web.routes`/Open.

**Required live evidence**

- repeat the most important failure drills against real two-node topology.

**Forbidden scope**

- no feature expansion;
- no v0.5 connection mechanism;
- no compatibility work for unapproved upstream DSH versions.

**Failure / stop conditions**

- hardening requires changing accepted routing/security semantics: return to architecture review.

**Stage completion criteria**

Known v0.4 failure modes fail closed and recover without target confusion or identity loss.

- `npm run check`;

**Required live evidence**

- final two-node mounted run using the exact executable candidate commit or a clearly documented docs-only closure ancestry;
- production-promotion plan showing how the current single-node public authority becomes the selector and how rollback restores the previous gateway mapping without changing node identity.

**Forbidden scope**

**Failure / stop conditions**

- release docs claim support for a DSH version without compatibility evidence;
- tag/publish/promotion occurs before final review.

**Stage completion criteria**

Stop at FINAL REVIEW. Tag/release/production promotion are separate operator actions authorized only after Final Review PASS.
