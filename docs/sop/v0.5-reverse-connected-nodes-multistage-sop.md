If implementation discovers that any of the following must change, **STOP** and return to architecture review:

- explicit `routeMode = direct | reverse` with no automatic fallback;
- pairing recovery boundaries;

- use of existing `ORBIT-ROUTE-V1` for each routed reverse flow;
- one control connection + bounded one-flow-per-data-channel pool;
- public reverse ingress path/method allowlist;
- separation of `registryContact`, reverse presence, reachability, DSH health, and compatibility;
- delete/reenroll identity rules;
- the 48-field acceptance matrix;
- v0.5 / v0.6 / v0.7 scope boundary.

Do not “solve” an implementation difficulty by changing one of those invariants in code.

## 2. Global construction rules

### 2.1 RFC-first gate

Before Gate A:

- documentation/tests that validate documentation/governance may change;
- no v0.5 product runtime implementation may be added under `src/**`, `bin/**`, `ui/**`, or production gateway configuration;
- RFC-0012 and this SOP may be reviewed/remediated.

After Gate A GO, product construction may begin.

### 2.2 DSH boundary

DSH remains an opaque execution runtime.

v0.5 must not encode in the Hub or reverse protocol:

- DSH cookie names or values;
- launch-token names;
- private RPC names;
- frontend component structure;
- plugin-private APIs;
- DSH model/settings/session semantics.

The reverse transport carries opaque RFC-0010 browser HTTP/WebSocket behavior. The existing compatibility policy still decides whether `web.routes` is available.

### 2.3 No general tunnel

All stages prohibit:

- arbitrary TCP destination forwarding;
- SOCKS;
- HTTP CONNECT proxying;
- VPN/service-mesh semantics;
- port discovery;
- node-requested destinations;
- remote shell/task execution on the reverse control channel.

A reverse data channel can be assigned only by the Hub to an already-authorized RFC-0010 route for that same node.

### 2.4 Explicit route mode

- Existing v0.4 nodes default to `direct`.
- Fresh paired nodes default to `reverse`.
- Operator changes are explicit and audited.
- Stored inactive alternate transport metadata does not create failover.
- No direct→reverse or reverse→direct automatic fallback may ever make a failed request succeed.

### 2.5 Evidence honesty

- `PASS` means executed and observed.
- Required but unexecuted work is `NOT_EXECUTED`.
- A failed real run is not overwritten by prose.
- Historical evidence may inform design but may not be rebound to a new candidate.
- Any post-freeze product/harness fix creates a new candidate and requires fresh candidate-bound evidence.

Names may vary, but responsibilities must stay separated.

Recommended seams:

```text

  pairing.*

  registry/sqlite.*    migration + durable pairing/route-mode state

src/node/
  reverse-client.*

ui/
  existing selector / node detail only

docker-registry/

test/
  pairing
  reverse control
  reverse channels
  reverse HTTP
  reverse WebSocket
  route-mode / no-fallback

```

Do not clone RFC-0010 routing policy into a “reverse router”. The existing route proxy chooses one immutable transport adapter after eligibility is decided.

# Stage 1: Registry migration, route mode, and pairing core

**Objective**

Add durable v0.5 bootstrap state without opening a public reverse channel yet.

**Implementation scope**

- schema v5 → v6 migration exactly as RFC-0012 D11;
- add `nodes.route_mode` with `direct|reverse`, defaulting all existing nodes to `direct`;
- extend existing `enrollment_tokens.purpose` with `pair` (pair rows unbound) and existing `enrollment_results.kind` with `pair`; do not create parallel pairing token/result tables;
- extend existing `/hub/tokens` create/list with `purpose=pair`; no separate pairing-token management API;
- pairing transaction and idempotency;
- fresh paired node creation with `routeMode = reverse`;
- reuse normal node Ed25519 identity and RFC-0008 Hub route identity provisioning;
- audit/events;
- backup/restore coverage.

Pairing may initially be exercised against the Hub directly in test fixtures. Public gateway exposure belongs to Stage 2.

**Required durable behavior**

- pairing token plaintext never persists;
- pairing token has purpose `pair` only;
- default TTL 10 min, accepted range 1–60 min;
- `pairingRequestId` exact replay returns exact result;
- different-content replay is denied;
- failed validation/transaction consumes nothing;
- active existing node cannot “pair again”;
- tombstoned same-node recovery remains RFC-0005 reenroll only;
- lost local private key → fresh pair → fresh node ID;
- v0.4 route target/identity/history survive migration unchanged.

**Required automated tests**

At minimum:

- schema v5 → v6 migration, including SQLite CHECK-domain rebuild correctness;
- migration rerun idempotent;
- all old nodes `routeMode=direct`;
- pair token digest-only;
- plaintext-once operator response;
- expired/wrong-purpose/unknown token denied;
- exact pairing replay idempotent;
- content-mismatch replay denied;
- transaction failure consumes nothing;
- fresh pair produces new node ID + node key + reverse route mode;
- pair cannot resurrect tombstone;
- existing node pair attempt denied;
- lost-key fresh pair produces a different node ID;
- pairing A never mutates node B;
- backup/restore preserves route mode + pair-purpose token/result/audit but no live reverse state;
- schema v6 table/column/index contract is exact and startup fails closed on malformed/future/corrupt variants.

**Required live evidence**

None beyond process-level integration fixtures.

**Forbidden scope**

- no public reverse gateway admission;
- no WebSocket control/data channel;
- no route proxy changes;
- no selector Open changes.

**Stop conditions**

- pairing creates a second long-lived identity model;
- pair token can recover old node ID;
- migration changes accepted direct routing behavior;
- any pair secret appears in logs/evidence.

**Completion**

Stage 1 is complete when persistence/bootstrap semantics are deterministic, migration-safe, and independently tested.

# Stage 2: Public reverse machine ingress and pairing bootstrap

**Objective**

Make the exact RFC-0012 public machine surfaces reachable over verified HTTPS/WSS without exposing the whole internal machine plane.

**Implementation scope**

Outer gateway admits exactly:

```text
POST /api/v1/pair
POST /api/v1/heartbeat
POST /api/v1/report-upload
POST /api/v1/credential-rotate
POST /api/v1/reenroll
GET  /api/v1/reverse/control
GET  /api/v1/reverse/channel
```

At this stage the reverse upgrade paths may fail closed after authentication because session/channel behavior is Stage 3/4.

`/api/v1/enroll` must remain non-public.

Public heartbeat/report/rotation/reenroll reuse existing RFC-0006 semantics without creating duplicate APIs.

**Required security behavior**

- HTTPS/WSS only;
- system/private CA trust with normal hostname/SAN validation;
- no `skipVerify`;
- wrong method/path rejected at gateway/ingress;
- browser cookies / operator gateway assertion stripped;
- no operator principal injected;
- reverse control/channel WebSocket upgrades must omit `Origin`; any `Origin` header is rejected with 403 before upgrade;
- machine signatures verified by existing machine auth;
- per-IP and protocol rate limits preserved;
- pair token redacted;
- reverse control/channel upgrades are native machine traffic and MUST omit `Origin`; any `Origin` header is rejected with 403 before upgrade;
- forwarded headers do not become identity.

**Required automated tests**

- exact path/method allowlist;
- `/api/v1/enroll` public request denied;
- unknown machine path denied;
- pair over public HTTPS succeeds with valid token and persists the public reverse ingress as the node's canonical `hubBaseUrl`;
- public heartbeat/report/rotation works only with valid machine signature;
- missing/wrong machine signature denied;
- timestamp skew denied;
- nonce replay denied;
- request signed for one path cannot authenticate another;
- gateway assertion/browser cookie cannot substitute for machine auth;
- unknown CA denied;
- wrong SAN denied;
- valid configured private CA succeeds;
- secrets absent from logs.

**Required live evidence**

One freshly paired node reaches the public Hub only through the new public machine ingress and successfully:

1. pairs;
2. heartbeats;
3. uploads a compatibility report;
4. receives/acknowledges normal RFC-0008 Hub route public material.

No reverse browser traffic yet.

**Stop conditions**

- public ingress exposes arbitrary `/api/v1/*`;
- browser session auth can enter machine API;
- machine API semantics diverge from RFC-0006;
- pairing needs an insecure TLS exception.

**Completion**

A NAT-capable node can bootstrap and maintain its existing machine/control-plane relationship entirely outbound.

# Stage 3: Reverse control session, presence, and reconnect

**Objective**

Create the authenticated Node→Hub reverse presence channel without carrying browser payload.

**Implementation scope**

- `GET /api/v1/reverse/control` WebSocket upgrade;
- authenticate upgrade using existing `ORBIT-MACHINE-V1` over GET + empty body hash;
- persistent nonce reservation;
- Hub-generated 128-bit reverse session ID;
- exact `session`, `ready`, `status`, ping/pong, `close` control vocabulary;
- one current ready session per node;
- provisional new connection → atomic takeover only after valid ready;
- old generation + channels invalidated on takeover;
- ping 20s / pong timeout 10s;
- node reconnect 1/2/4…30 seconds ±20% jitter;
- deterministic `reversePresence`: current ready session → `online`; reverse-mode node without a ready session → `offline`; direct-mode node without a reverse session → `unknown`;
- reverse-mode `reachable` driven by current session + generic local DSH route readiness;
- no browser transport.

**Required automated tests**

- valid active node connects;
- tombstoned/revoked node denied;
- A signature cannot connect as B;
- nonce replay denied;
- stale timestamp denied;
- invalid protocol/version fails closed;
- only one current ready generation;
- unready newcomer cannot evict healthy session;
- ready newcomer deterministically supersedes old generation;
- late old disconnect cannot clear new session;
- control loss → presence offline;
- reconnect → online;
- local DSH readiness false changes `reachable`, not `registryContact`;
- heartbeat loss changes `registryContact`, not reverse session identity;
- Hub restart creates no phantom online state;
- Node restart reconnects with same node ID/key;
- no control message can execute arbitrary command/DSH RPC.

**Required live evidence**

- reverse node connects from an outbound-only network position using its canonical persisted `hubBaseUrl`;
- disconnect/reconnect cycle;
- Hub restart + automatic node reconnect;
- Node restart + reconnect;
- local DSH stop/restart changes reverse reachability independently.

**Forbidden scope**

- no browser HTTP body;
- no data-channel pool;
- no selector route via reverse yet.

**Stop conditions**

- control session becomes a command queue;
- session state persisted/restored as online;
- old generation can mutate new generation.

**Completion**

Presence/reconnect is deterministic and independently observable, while browser routing remains disabled.

# Stage 4: Bounded data-channel pool and reverse HTTP

**Objective**

Carry ordinary RFC-0010 HTTP through reverse transport without creating multiplexed tunnel complexity.

**Implementation scope**

- authenticated `/api/v1/reverse/channel` upgrade;
- bind channel to current node + reverse session;
- default idle target 8, max 32; enforce RFC bounds;
- channel state `connecting → idle → busy → idle/closed`;
- one flow per channel;
- 2-second same-node capacity wait then 503 `reverse-capacity`;
- OPEN / request binary / request-end / response / response binary / response-end / abort / idle protocol;
- existing `ORBIT-ROUTE-V1` proof embedded in OPEN and verified node-side;
- HTTP method/raw target/header semantics match RFC-0010;
- request and response bodies stream;
- RFC-0010 cookie isolation remains intact;
- bounded queues and stall timeout exactly per RFC-0012 D7;
- route proxy transport adapter may target reverse HTTP only in test/internal mode; public selector Open remains blocked until Stage 5 completes WebSocket parity.

**Required automated tests**

- channel requires machine auth + current session;
- A channel cannot bind B session;
- stale session ID denied;
- old-session channel closes after takeover;
- pool min/max validation;
- pool replenishment never exceeds max;
- no idle capacity waits ≤2s then 503;
- no fallback;
- OPEN requires valid ORBIT-ROUTE-V1;
- wrong node/authority/path/replay denied before DSH;
- one `ORBIT-ROUTE-V1` proof cannot be accepted once on direct ingress and again on reverse transport within the same node process;
- root HTTP;
- static asset;
- status transparency;
- header sanitation;
- host/authority preservation;
- streaming upload without whole-body buffering;
- large response streaming;
- downstream abort;
- browser abort;
- channel desync closes instead of guessing;
- 64 KiB data frame split;
- 512 KiB soft / 2 MiB hard bounds;
- 30s stall timeout;
- completed HTTP channel returns idle safely;
- no route/machine credentials reach DSH.

**Required live evidence**

Reverse node serves:

- DSH root;
- static asset;
- API response;
- streaming upload;
- multi-request page burst using pool reuse.

**Forbidden scope**

- no general multiplexing;
- no WebSocket reverse route yet;
- no direct/reverse automatic fallback.

```text
Stage:
Exact HEAD:
Parent / baseline:
Branch:
Local/remote divergence:
Changed files:
Scope check:
Focused tests:
Full tests:
Live evidence:
Known NOT_EXECUTED:
P0/P1/P2 self-review:
Requested next gate:
```

Do not write “all done” without exact SHA/test/evidence.

## 5. Stop-work matrix

Immediately STOP the current stage and request review if any of these occur:

| Finding | Action |
| --- | --- |
| Need new public node authority | architecture review |
| Need new selector model | architecture review |
| Need automatic failover | architecture review |
| Need multiplex/general tunnel | architecture review |
| Need new DSH compatibility profile | separate DSH profile RFC/policy |
| Pair token can restore historical node ID | security blocker |
| Reverse channel bypasses ORBIT-ROUTE-V1 | security blocker |
| Public gateway needs wildcard machine API | security blocker |
| TLS verification must be disabled | security blocker |
| Queue/channel resource cannot be bounded | security blocker |
| Product/harness fix after candidate freeze | new candidate + fresh evidence |
| Mounted field unexecuted | NOT_EXECUTED / no PASS |
| Cleanup leaves secret/process/profile residue | no PASS |
| 0.6/0.7 feature needed | defer; do not absorb into v0.5 |

## 6. Definition of done for v0.5 engineering acceptance

v0.5 is engineering-complete only when:

- RFC-0012 is accepted;
- all Stage 0–8 gates are closed;
- direct v0.4 routing still passes;
- reverse pairing/control/data lifecycle passes;
- exact 48-field matrix is all PASS;
- canonical mounted topology proves a genuinely reverse-only node;
- seven evidence artifacts are candidate-bound and hash/byte verified;
- evidence closure is direct child of the frozen candidate;
- closure full tests are green;
- residue is zero;
- Independent Final Review is P0=0/P1=0/P2=0 PASS.

Anything less remains construction/qualification, not accepted v0.5.
