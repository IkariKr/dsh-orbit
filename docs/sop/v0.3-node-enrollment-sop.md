# DSH Orbit v0.3 Node enrollment SOP

This procedure uses the frozen `ORBIT-MACHINE-V1` and
`ORBIT-REENROLL-V1` contracts. The Node private key stays in the Node state
file and never leaves the Node.

## Prepare the Node

1. Create a dedicated state path and protect it at POSIX mode `0600`.
2. Set the persistent shell or service environment below, replacing the
   example values with the installed Node's actual paths and versions.
3. Do not put plaintext tokens or private keys in scripts, logs, or evidence.

### Persistent shell/service environment

Load this block once in the shell that launches Node CLI processes. For a
service, put the same variables in its service environment or environment file
so every Node CLI process inherits them; do not set them only on the enrollment
command.

```sh
export DSH_ORBIT_NODE_STATE='/path/node-state.json'
export DSH_ORBIT_HUB_URL='http://private-registry.example/'
export DSH_ORBIT_NODE_ORBIT_VERSION='0.3.0'
export DSH_ORBIT_NODE_ORBIT_REVISION='installed-orbit-revision'
export DSH_ORBIT_NODE_DSH_VERSION='installed-dsh-version'
export DSH_ORBIT_NODE_DSH_PROFILE='installed-dsh-profile'
export DSH_ORBIT_NODE_HEARTBEAT_SECONDS='60'
```

These seven variables must remain visible in the environment of **every** Node
CLI process (`enroll`, `status`, `run`, `upload-report`, `rotate`, and
`reenroll`). They are process configuration, not Node state: the CLI reads them
at each process start, never restores them from the state file, and must not
silently substitute values recovered from state. Keep this block loaded for
operator commands and for the service that runs the heartbeat loop.

Do not add `DSH_ORBIT_ENROLL_TOKEN`, `DSH_ORBIT_REENROLL_TOKEN`, or
`DSH_ORBIT_REPORT_FILE` to this persistent block. Those sensitive token/file
values are supplied inline only for the command that needs them.

## Initial enrollment

An operator mints an `enroll` token through the authenticated browser surface.
With the persistent environment loaded, run:

```sh
DSH_ORBIT_ENROLL_TOKEN='one-time-token' node bin/dsh-orbit-node.mjs enroll
```

The command prints the Node ID and key ID. The token is not stored. Confirm the
state file is `active`:

```sh
node bin/dsh-orbit-node.mjs status
```

Then start the heartbeat loop:

```sh
node bin/dsh-orbit-node.mjs run
```

`run` is a long-running process. Start it under the service environment, or
from another shell that has loaded the same persistent block before issuing
later operator commands.

## Reports and status

Upload a validated compatibility report with its file path inline for this
command only:

```sh
DSH_ORBIT_REPORT_FILE='/path/report.json' node bin/dsh-orbit-node.mjs upload-report
```

Use `status` for local identity and lifecycle state, and `doctor` for
non-mutating local integrity and reachability checks. A report contributes
compatibility evidence and capabilities; only an authenticated heartbeat
controls Registry contact freshness.

## Restart

Restart with the same persistent environment, state path, and exactly the same
canonical Hub URL:

```sh
node bin/dsh-orbit-node.mjs status
node bin/dsh-orbit-node.mjs run
```

The Node keeps its node ID and current key. A pending rotation is resolved by
commit detection; restart never creates a third rotation key and never
automatically reenrolls a revoked Node.

## Credential rotation

With the persistent environment loaded, run:

```sh
node bin/dsh-orbit-node.mjs rotate
```

The intent is persisted before the request. If the response is uncertain, the
same pending key is probed and either promoted after commit detection or
resubmitted under the old key. Do not delete the state file during recovery.

## Revocation and reenrollment

A Hub delete changes the Node to a tombstone and the Node becomes locally
`revoked` after an authenticated denial. Reenrollment is an explicit operator
workflow. With the persistent environment loaded, provide the token inline:

```sh
DSH_ORBIT_REENROLL_TOKEN='tombstone-bound-token' node bin/dsh-orbit-node.mjs reenroll
```

Retry with the same token if the response is uncertain. The persisted pending
request and key are replayed exactly, the original node ID is restored, and no
new node ID is minted. A revoked Node must not reenroll automatically.

## Failure handling

- `unknown-key`, timestamp, replay, rate-limit, and 5xx outcomes do not by
  themselves persist `revoked`.
- A Hub binding mismatch fails closed.
- A corrupt or permissive state file fails closed; do not edit it in place.
- Preserve the state file and consult [`../troubleshooting.md`](../troubleshooting.md)
  before retrying an identity-changing operation.

See [`../node-registry-client.md`](../node-registry-client.md) for the complete
state schema and [`../configuration-reference.md`](../configuration-reference.md)
for environment variables.
