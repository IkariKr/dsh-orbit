# DSH Orbit v0.2 Upgrade Guard Multi-Stage SOP

Status: Complete
Target release: `v0.2.0` (delivered; revalidated after review remediation in `v0.2.1` through `v0.2.5`, see `docs/release-attestations/`)
Applies to: DSH Orbit maintainers and downstream production operators  
Primary goal: turn the existing documented DSH upgrade guidance into a repeatable, fail-closed, testable, auditable, and rollback-safe upgrade workflow before fleet features are introduced.

## 1. Purpose

DSH Orbit `0.1.x` establishes the secure remote-deployment and compatibility baseline around DeepSeek Harness (DSH). The next development phase should not add fleet routing or multi-node execution yet. It should first make single-node production upgrades operationally safe.

This SOP defines the staged work required to deliver the `v0.2 Upgrade Guard` milestone. Each stage has explicit tasks, outputs, acceptance criteria, failure conditions, and an entry gate for the next stage.

The expected end state is:

1. a known-good production baseline is recorded and recoverable;
2. candidate DSH versions can be built without replacing production;
3. compatibility is checked against explicit profiles and exact source layouts;
4. positive and negative authorization behavior is exercised against a live candidate deployment;
5. persistent data is snapshotted before promotion;
6. a pre-upgrade session can be resumed against copied candidate data;
7. a machine-readable and human-readable compatibility report is generated;
8. production promotion remains an explicit operator action;
9. upstream DSH releases can be detected without being automatically promoted or declared supported;
10. fleet work begins only after the upgrade guard is stable.

## 2. Scope

### 2.1 In scope

- freezing and tagging the current `v0.1.1` production baseline;
- live negative-authorization smoke tests;
- compatibility report generation;
- snapshot and rollback contracts;
- candidate build and verification orchestration;
- upgrade integration tests;
- upstream DSH version detection in CI;
- production rehearsal using copied data;
- release readiness for `v0.2.0`;
- RFC preparation for the later `0.3` node-registry milestone.

### 2.2 Out of scope

The following must not be implemented as part of this SOP:

- fleet dashboard;
- multi-node session routing;
- reverse-connected nodes;
- fleet-wide command broadcast;
- central task scheduling;
- Kubernetes-specific orchestration;
- PostgreSQL or Redis introduced solely for future fleet needs;
- large-scale repository or CLI-framework rewrites that are not required by the upgrade guard;
- broad RBAC design for future multi-node operation.

## 3. Global engineering constraints

All stages must preserve the existing project principles.

### 3.1 Upstream first

Before adding a DSH compatibility workaround, verify whether the target DSH release already provides an official capability with equivalent security properties. Prefer upstream support whenever possible.

### 3.2 Fail closed

Unknown DSH versions, source-layout mismatches, failed security checks, failed snapshots, failed compatibility checks, or incomplete reports must stop the affected upgrade path. The upgrade workflow must not silently downgrade a hard failure to a warning.

### 3.3 Production promotion is explicit

No automation introduced by this SOP may automatically promote a candidate to production. Automation may detect, build, test, report, and prepare. Final production promotion remains an explicit operator action.

### 3.4 No secret leakage

Logs, reports, fixtures, CI artifacts, and generated manifests must not include:

- proxy shared secrets;
- Basic Auth passwords;
- access tokens;
- identity-provider assertions;
- user settings secrets;
- session private content;
- downstream certificate private keys.

### 3.5 Compatibility is evidence-based

A version is not supported merely because a container image builds. Support requires the compatibility and runtime evidence described by this SOP and `docs/compatibility.md`.

### 3.6 Keep the layer small

DSH Orbit remains a compatibility, deployment, and future control-plane layer around DSH. It must not evolve into a fork or replacement runtime as part of this work.

## 4. Stage dependency overview

```text
Stage 0  Freeze v0.1.1 baseline
   |
   v
Stage 1  Live authorization smoke suite
   |
   v
Stage 2  Compatibility report
   |
   v
Stage 3  Snapshot and rollback contract
   |
   v
Stage 4  Candidate upgrade runner
   |
   v
Stage 5  Upgrade integration tests
   |
   v
Stage 6  Upstream compatibility watcher
   |
   v
Stage 7  Production rehearsal and v0.2 release
   |
   v
Stage 8  v0.3 fleet RFC preparation only
```

A later stage must not be considered complete while a required earlier stage is incomplete.

# Stage 0 - Freeze the v0.1.1 production baseline

## Goal

Create a formally recorded known-good baseline before introducing the `v0.2` upgrade machinery. This baseline is the recovery reference for both source and production runtime behavior.

## Preconditions

- repository `main` is clean;
- `main` matches the intended public remote branch;
- `package.json` and `CHANGELOG.md` identify version `0.1.1`;
- the current production downstream deployment is reachable for validation;
- the currently deployed DSH version is known.

## Tasks

### 0.1 Repository validation

Run the existing repository checks:

```sh
npm run check
```

Also validate shell entrypoints used by the container where applicable.

### 0.2 Record source identity

Record at minimum:

- DSH Orbit version;
- exact Git commit SHA;
- Git tag, once created;
- DSH version;
- compatibility profile;
- container image tag or digest used by production;
- downstream deployment identifier or environment name, without secrets.

### 0.3 Production behavior validation

Validate the known-good deployment against the current `0.1.x` requirements:

- DSH web UI loads through the intended authenticated gateway;
- lazy-loaded plugin assets/routes load through the public host;
- `settings.describe` succeeds;
- a no-op `settings.mutate` succeeds;
- one session created before the latest DSH change resumes successfully;
- the session can re-select its current model without changing the model choice;
- WebSocket or long-running agent traffic remains functional;
- a sidebar terminal opens;
- `dsh --version` runs from the terminal;
- the persisted profile's `node-pty` binding is healthy;
- the DSH service itself is not directly published to an untrusted LAN or public interface.

### 0.4 Tag the baseline

After the above checks pass:

- create Git tag `v0.1.1` at the verified commit;
- publish the tag;
- create a GitHub release if the repository release process uses GitHub Releases;
- ensure the changelog accurately reflects the tagged state.

### 0.5 Preserve rollback references

Record the previous production image and a known-good data recovery point according to downstream production procedures.

## Deliverables

- `v0.1.1` Git tag;
- recorded source commit and DSH version;
- production validation evidence;
- known-good image reference;
- known-good data recovery reference.

## Acceptance criteria

Stage 0 passes only if all of the following are true:

- `npm run check` passes;
- the production checks above pass;
- the exact Orbit commit and DSH version are recorded;
- `v0.1.1` points to the tested commit;
- an operator can identify both the source/image rollback target and the persistent-data rollback target.

## Failure conditions

Do not proceed if:

- repository validation fails;
- the production session-resume test fails;
- the terminal or plugin path is broken;
- production identity cannot be tied to an exact Orbit revision;
- rollback data is unknown or unavailable.

## Gate to Stage 1

Stage 1 starts only after `v0.1.1` is a reproducible known-good baseline.

# Stage 1 - Implement the live authorization smoke suite

## Goal

Prove authorization behavior against a running candidate deployment, not only through patch-source inspection and unit tests.

## Tasks

### 1.1 Add a dedicated smoke entrypoint

Introduce a script such as:

```text
scripts/smoke-auth.mjs
```

and expose it through `package.json`, for example:

```text
npm run smoke:auth
```

The exact command name may differ, but the function must remain focused and independently runnable.

### 1.2 Positive control

Verify an authenticated, expected-origin request can reach a safe privileged RPC such as `settings.describe`.

This test is required so that a suite cannot pass merely because the service rejects every request.

### 1.3 Unauthenticated request

Send a request through the externally reachable candidate route without the required user authentication. The request must not gain privileged access.

### 1.4 Invalid user authentication

Where the tested route supports Basic Auth or another testable local authentication mechanism, verify invalid credentials are rejected.

### 1.5 Cross-origin request

Send an otherwise valid request with an unexpected `Origin`. Privileged access must be rejected.

### 1.6 Cross-site browser request

Send an otherwise valid request with:

```text
Sec-Fetch-Site: cross-site
```

Privileged access must be rejected.

### 1.7 Identity-provider assertion spoofing

For the local/LAN proxy path, verify a client-supplied identity-provider assertion header such as `Cf-Access-Jwt-Assertion` cannot be used to bypass the intended access boundary.

The test must reflect the documented proxy topology rather than assuming the header is inherently trustworthy.

### 1.8 Error handling and redaction

Smoke output must:

- clearly identify which case failed;
- avoid printing credentials or proxy secrets;
- avoid echoing full sensitive response bodies;
- use a non-zero exit code for any failed required case.

### 1.9 Unit tests

Add unit tests for request construction, expected status classification, configuration validation, and secret redaction behavior where practical.

## Deliverables

- live authorization smoke script;
- package script entry;
- test coverage for the smoke helper logic;
- documentation describing required environment variables and supported auth path.

## Acceptance criteria

The suite must prove all required outcomes:

| Case | Expected result |
| --- | --- |
| authenticated, expected origin | allowed |
| unauthenticated | denied |
| invalid credentials | denied |
| unexpected `Origin` | denied |
| `Sec-Fetch-Site: cross-site` | denied |
| forged identity assertion on local path | denied |

Additional acceptance criteria:

- the suite returns non-zero on any required mismatch;
- credentials and internal secrets are absent from normal and failure output;
- `npm run check` passes with the new tests.

## Failure conditions

Stage 1 fails if:

- any negative case is accepted;
- the positive control cannot pass;
- the test requires exposing the internal Orbit proxy secret to the browser/client;
- the suite only checks source text instead of making live requests;
- failure output leaks sensitive material.

## Gate to Stage 2

A live candidate endpoint must be able to produce a deterministic authorization smoke result before compatibility reporting is built around it.

# Stage 2 - Implement compatibility report generation

## Goal

Produce a sanitized, reproducible evidence record for each candidate validation run.

## Tasks

### 2.1 Define report schema

Create a small, versioned report schema. It should include at minimum:

- report schema version;
- generation timestamp;
- Orbit version;
- Orbit Git revision when available;
- candidate DSH version;
- selected compatibility profile;
- global compatibility patch status;
- profile-local compatibility patch status;
- web/runtime readiness status;
- settings read status;
- settings no-op write status;
- authorization smoke status;
- historical session-resume status;
- terminal/PTTY status when tested;
- snapshot reference when applicable;
- overall decision.

### 2.2 Provide machine-readable output

Support JSON output suitable for:

- CI artifacts;
- downstream archival;
- future Hub display;
- automated comparison.

### 2.3 Provide human-readable output

Provide a concise terminal/report summary that allows an operator to answer:

- what exact candidate was tested;
- which checks ran;
- which checks passed or failed;
- whether the candidate is eligible for manual promotion.

### 2.4 Separate facts from decision

The report must distinguish raw evidence from the final decision. For example, a supported source layout alone must not produce `PASS` if session resume or authorization tests failed.

### 2.5 Redact sensitive data

Implement explicit tests that prove the report does not include configured secrets or credentials.

### 2.6 Deterministic failure reporting

Missing required evidence must be represented as `not_run`, `missing`, or an equivalent explicit state. It must not be silently treated as pass.

## Deliverables

- report schema and implementation;
- JSON output mode;
- human-readable output mode;
- report-focused tests;
- documentation of status meanings.

## Acceptance criteria

Stage 2 passes when:

- a candidate run produces both machine-readable and human-readable reports;
- the report records exact Orbit and DSH identities where available;
- every required check has an explicit state;
- an unexecuted required check cannot yield an overall pass;
- tests demonstrate secret redaction;
- `npm run check` passes.

## Failure conditions

Do not proceed if:

- the report can claim success while required checks were skipped;
- the report exposes credentials or session content;
- the report cannot identify the tested DSH version or Orbit revision;
- report status is derived only from successful image build.

## Gate to Stage 3

A candidate validation run must be able to emit structured evidence before snapshot and rollback metadata are incorporated.

# Stage 3 - Define and implement the snapshot and rollback contract

## Goal

Make persistent-data protection a required, machine-checkable step without forcing one storage technology on downstream deployments.

## Design rule

DSH Orbit should define the contract and orchestration boundary. The downstream operator may implement the actual snapshot with ZFS, Btrfs, NAS snapshots, reflinks, `rsync`, VM snapshots, or another reviewed method.

## Tasks

### 3.1 Define snapshot hook contract

Define a stable invocation contract for downstream snapshot logic. The contract must specify:

- required inputs;
- expected exit behavior;
- output/manifest location;
- timeout behavior if applicable;
- secret-handling requirements;
- what constitutes a completed snapshot.

Reuse the existing fail-closed downstream-hook philosophy where practical rather than creating a parallel plugin system.

### 3.2 Define snapshot manifest

The generated manifest should contain at minimum:

- snapshot ID;
- creation timestamp;
- Orbit revision;
- DSH version;
- data-root identifier/path or logical name;
- snapshot method identifier;
- downstream-provided restore reference;
- completion status.

The manifest must not embed storage credentials.

### 3.3 Require snapshot completion before promotion

The future candidate runner must refuse promotion readiness when a required production snapshot has failed or is incomplete.

### 3.4 Document copied-data candidate testing

Define how the operator creates and identifies a copied data set for candidate testing. Candidate testing must not mutate the only known-good production copy.

### 3.5 Define rollback contract

Document rollback as two independently tracked operations:

1. restore the last known-good image/source revision;
2. restore the corresponding persistent-data snapshot when the candidate may have changed persistent data.

### 3.6 Add failure-path tests

Test at minimum:

- snapshot hook success;
- snapshot hook non-zero exit;
- missing manifest;
- invalid/incomplete manifest;
- redaction of sensitive fields;
- promotion-readiness denial after snapshot failure.

## Deliverables

- snapshot hook contract;
- snapshot manifest schema;
- rollback documentation;
- implementation needed to invoke/validate the snapshot contract;
- tests for success and failure paths.

## Acceptance criteria

Stage 3 passes when:

- at least one reference downstream snapshot implementation can satisfy the contract;
- a failed snapshot stops the upgrade readiness path;
- the manifest identifies the recovery point without secrets;
- copied-data candidate testing is documented;
- rollback explicitly includes both image and data recovery where required;
- `npm run check` passes.

## Failure conditions

Do not proceed if:

- snapshot failure can be downgraded to a warning while promotion remains eligible;
- the design assumes one filesystem or NAS vendor;
- the only rollback plan is “use the old container image”;
- candidate validation must run directly against the sole production data copy.

## Gate to Stage 4

Snapshot success/failure and restore references must be machine-readable before the candidate workflow is orchestrated end to end.

# Stage 4 - Implement the candidate upgrade runner

## Goal

Turn the documented manual upgrade sequence into a small, explicit orchestration command while preserving human-controlled production promotion.

## Tasks

### 4.1 Introduce a focused upgrade command

Add a small command surface, for example:

```text
dsh-orbit-upgrade preflight
dsh-orbit-upgrade candidate
dsh-orbit-upgrade verify
dsh-orbit-upgrade report
```

The exact interface may change during implementation. Avoid adopting a large CLI framework unless required by actual complexity.

### 4.2 Preflight checks

Preflight should validate at minimum:

- candidate DSH version is supplied;
- `DSH_PUBLIC_HOST` and other required non-secret configuration are valid;
- candidate version has a compatibility profile when running in supported mode;
- required downstream directories are available;
- production baseline identity is known;
- a historical session ID is supplied when the session-resume gate is required;
- snapshot capability is configured for production promotion readiness.

### 4.3 Candidate build

Build a new image/tag without replacing the running production image.

Build must fail if:

- the DSH version is unsupported;
- an exact patch source matcher fails;
- the global patch cannot be verified.

### 4.4 Candidate copied-data start

Start the candidate against copied data and an isolated candidate endpoint or port. It must not take over the production route during validation.

### 4.5 Candidate verification sequence

Execute, in a deterministic order, the required checks:

1. container/runtime readiness;
2. global and profile-local patch verification;
3. authenticated settings read;
4. no-op settings write;
5. live authorization smoke suite;
6. existing-session resume and current-model re-selection;
7. web/plugin route check;
8. long-lived transport/WebSocket check where automated support exists;
9. terminal/PTTY check where automated support exists;
10. compatibility report generation.

### 4.6 Stop on hard failure

Required failures must stop the candidate decision path. The runner may still finalize a failure report, but it must not continue toward a successful promotion-ready state.

### 4.7 No automatic production promotion

The command may output a final state such as:

```text
CANDIDATE PASSED - ELIGIBLE FOR MANUAL PROMOTION
```

It must not switch the production deployment automatically.

## Deliverables

- candidate upgrade command;
- preflight implementation;
- candidate build/start/verify orchestration;
- integration with smoke suites and report generation;
- documented exit codes or status semantics.

## Acceptance criteria

Stage 4 passes when a maintainer can execute one documented candidate workflow that:

- leaves production running during candidate validation;
- rejects unsupported or source-mismatched DSH versions;
- runs all required candidate checks;
- generates a final report;
- returns non-zero on required failure;
- never performs automatic production promotion.

## Failure conditions

Do not proceed if:

- the runner overwrites the last known-good image tag;
- candidate startup mutates the only production data copy;
- a required failed check still produces `candidate passed`;
- the command automatically replaces production;
- failure behavior depends on manual reading of logs rather than exit/status semantics.

## Gate to Stage 5

The candidate workflow must function end to end before broad integration and failure-injection tests are considered complete.

# Stage 5 - Add upgrade integration and failure-path tests

## Goal

Prove that the upgrade guard fails safely under the conditions it is specifically designed to catch.

## Tasks

### 5.1 Supported candidate path

Test the known supported DSH profile through the candidate workflow using fixtures or controlled containers where practical.

### 5.2 Unsupported DSH version

Verify an unknown version is rejected before it can be marked supported or promotion-ready.

### 5.3 Source-layout drift

Change a fixture so an exact patch fragment is missing or duplicated. Verify fail-closed behavior.

### 5.4 Profile-local patch failure

Simulate failure to patch or verify the profile-local package. Candidate readiness must fail.

### 5.5 Authorization regression

Simulate at least one negative authorization case becoming accepted. The candidate must fail.

### 5.6 Session-resume regression

Exercise the known class of historical-session failures, including the diagnostic path for errors such as:

```text
agent-presets: refusing to compose an unscoped context
```

The candidate must fail while preserving a useful report.

### 5.7 Snapshot failure

Simulate snapshot hook failure and missing/invalid snapshot manifests. Promotion readiness must fail.

### 5.8 Terminal/PTTY regression

Where the runtime check is automated, simulate or fixture a missing `node-pty` native binding and verify the candidate cannot falsely pass the terminal requirement.

### 5.9 Report completeness

Verify each failed integration case produces a final sanitized report identifying the failed gate and never reports overall success.

## Deliverables

- integration tests;
- failure-injection fixtures;
- regression coverage for all upgrade gates;
- CI execution of repository-safe integration tests.

## Acceptance criteria

Stage 5 passes only if:

- all expected-success cases pass;
- every required failure case fails closed;
- failure reports remain available and sanitized;
- no test requires production credentials;
- `npm run check` passes;
- the test suite remains reasonable for public CI, with heavier live-environment tests clearly separated if necessary.

## Failure conditions

Do not proceed if a test demonstrates any path where:

- unsupported DSH becomes promotion-ready;
- a required auth failure is ignored;
- snapshot failure is ignored;
- session-resume failure is ignored;
- a missing required check is interpreted as pass.

## Gate to Stage 6

The upgrade guard must be demonstrably fail-closed before CI begins watching upstream releases automatically.

# Stage 6 - Add an upstream DSH compatibility watcher

## Goal

Detect new upstream DSH releases early without automatically modifying the compatibility registry or production deployment.

## Tasks

### 6.1 Scheduled CI workflow

Add a scheduled GitHub Actions workflow that checks the published DSH package version at a reasonable cadence.

### 6.2 Compare against compatibility registry

Classify the observed version as:

- already supported;
- known but not supported, if such a state is later represented;
- unknown candidate.

### 6.3 Unknown version handling

For an unknown release, the workflow may:

- record the detected version;
- attempt a non-production candidate build or patch-compatibility check;
- upload logs/reports as CI artifacts;
- open or update a compatibility issue if the project chooses to automate issue creation.

It must not:

- add the version to `src/compatibility.mjs` automatically;
- weaken existing exact source matchers;
- publish a support claim automatically;
- deploy to production.

### 6.4 Stable reporting

The watcher should produce a concise result that maintainers can triage without exposing secrets or downstream information.

### 6.5 Manual review path

Document the maintainer process for an unknown version:

1. inspect upstream release/source change;
2. determine whether upstream now removes the need for an Orbit patch;
3. create a new compatibility profile when required;
4. run the full candidate workflow;
5. update `docs/compatibility.md` only after evidence passes.

## Deliverables

- scheduled CI workflow;
- registry comparison logic;
- unknown-version artifact/report behavior;
- maintainer documentation.

## Acceptance criteria

Stage 6 passes when:

- CI can detect a version absent from the registry;
- an unknown version cannot become supported without a reviewed repository change;
- watcher failures do not affect production;
- no downstream secret or production endpoint is required for the public scheduled check;
- repository CI remains green.

## Failure conditions

Do not proceed if:

- the watcher can modify support state without review;
- a newly published DSH package triggers automatic deployment;
- the workflow requires production secrets merely to detect a new package version.

## Gate to Stage 7

The repository must be able to detect upstream change safely before the full `v0.2` production rehearsal and release.

# Stage 7 - Production rehearsal, release candidate, and v0.2.0 release

## Goal

Exercise the complete upgrade guard against the real downstream deployment pattern and release `v0.2.0` only after the workflow proves operationally useful.

## Preconditions

Stages 0 through 6 are complete.

## Tasks

### 7.1 Select a rehearsal candidate

Use either:

- the currently supported DSH version rebuilt through the new workflow; or
- a newly reviewed DSH version with an explicit compatibility profile.

Do not use an unreviewed unknown release merely to complete the rehearsal.

### 7.2 Snapshot production

Invoke the production snapshot contract and verify the manifest and restore reference before any promotion activity.

### 7.3 Create copied candidate data

Prepare an isolated copy of production DSH data for candidate testing.

### 7.4 Run candidate workflow

Run the complete candidate workflow against the isolated endpoint and copied data.

Required checks include:

- compatibility patch verification;
- runtime readiness;
- web/plugin route behavior;
- settings read/write smoke;
- live negative authorization suite;
- historical session resume;
- long-lived traffic/WebSocket behavior;
- terminal/PTTY behavior;
- compatibility report generation.

### 7.5 Review candidate report

A maintainer/operator must review the report before promotion. `CANDIDATE PASSED` is necessary but not sufficient to remove the explicit human decision.

### 7.6 Manual production promotion

Promote by an explicit operator action using a pinned Orbit revision and immutable image identity.

### 7.7 Post-promotion verification

Repeat the relevant smoke tests through the production route after promotion.

### 7.8 Rollback rehearsal or validation

Verify that the recorded last-known-good image and snapshot references are sufficient to execute rollback. A destructive rollback rehearsal is not required on production, but the restore procedure must be concrete and reviewed.

### 7.9 Documentation reconciliation

Update at minimum:

- `README.md` if user-facing commands changed;
- `docs/upgrade.md`;
- `docs/compatibility.md`;
- `docs/downstream-production.md`;
- `docs/roadmap.md`;
- `CHANGELOG.md`.

### 7.10 Release preparation

Before tagging `v0.2.0`:

- run `npm run check`;
- inspect the public tree for leaked environment-specific data;
- ensure documentation matches actual commands;
- ensure examples remain placeholder-based;
- verify the package/project version is consistent;
- tag the exact tested commit.

## Deliverables

- successful downstream production rehearsal;
- archived candidate compatibility report;
- snapshot manifest/recovery reference;
- updated public documentation;
- `v0.2.0` release tag and release notes.

## Acceptance criteria

`v0.2.0` is release-ready only when:

- the candidate workflow passes against the downstream production pattern;
- the live negative authorization suite passes;
- a pre-upgrade session resumes successfully on copied candidate data;
- production has a verified snapshot before promotion;
- production promotion remains manual;
- post-promotion smoke checks pass;
- rollback references are known;
- public-tree and test checks pass;
- no secrets or machine-specific deployment data enter the public repository.

## Failure conditions

Do not tag `v0.2.0` if:

- any required smoke check fails;
- production snapshot status is incomplete;
- the historical session test was skipped without an explicit documented exception approved by maintainers;
- the tested commit differs from the tagged commit;
- documentation describes commands or behavior that were not actually validated.

## Gate to Stage 8

Fleet design work may start only after `v0.2.0` is released or the maintainers explicitly document why the upgrade guard is considered stable enough to proceed.

# Stage 8 - Prepare v0.3 fleet RFCs without implementing fleet behavior

## Goal

Define the contracts needed for node registration before building a Hub UI, node router, or multi-node execution behavior.

## Tasks

Create RFCs under a dedicated documentation path such as:

```text
docs/rfc/
  0001-node-identity.md
  0002-node-capabilities.md
  0003-node-authentication.md
  0004-node-health.md
```

### 8.1 Node identity RFC

Define separate concepts for:

- stable node ID;
- installation ID where needed;
- user-facing display name;
- mutable hostname/address metadata.

A hostname or IP address alone must not be the stable identity.

### 8.2 Capability advertisement RFC

Prefer capability negotiation over UI branches keyed only to DSH versions.

Potential capability namespaces may include:

```text
sessions.resume
settings.remote
terminal.pty
agents.run
```

The RFC must define capability versioning and unknown-capability behavior.

### 8.3 Node authentication RFC

Define per-node credentials with:

- independent revocation;
- rotation;
- least privilege;
- no mandatory fleet-wide permanent shared secret.

### 8.4 Health model RFC

Define health as multiple dimensions rather than a single boolean. At minimum consider:

- reachable;
- authenticated;
- DSH healthy;
- Orbit compatible;
- capabilities known;
- last-seen metadata.

### 8.5 Upgrade-guard integration

Each RFC must explain how node registration and future Hub state consume the compatibility evidence produced by `v0.2` rather than creating a separate compatibility model.

## Deliverables

- reviewed RFC documents;
- explicit unresolved questions;
- no production fleet implementation yet.

## Acceptance criteria

Stage 8 is complete when maintainers can answer, on paper and consistently:

- what uniquely identifies a node;
- how a node proves its identity;
- how credentials are revoked and rotated;
- how capabilities are represented;
- how node health is represented;
- how Orbit/DSH compatibility status reaches the future Hub;
- what actions require explicit node target scope.

## Failure conditions

Do not begin fleet implementation if the design still relies on:

- IP or hostname as stable identity;
- one permanent credential shared by every node;
- `online: true/false` as the complete health model;
- DSH version numbers as the only capability mechanism;
- implicit broadcast behavior for commands or setting mutations.

# 5. Cross-stage Definition of Done

The overall `v0.2 Upgrade Guard` initiative is complete only when all of the following are true.

## Repository and build

- `npm run check` passes;
- supported DSH candidates can be built;
- unknown DSH versions fail closed;
- source-layout mismatches fail closed;
- public-tree validation finds no secrets or downstream-specific state.

## Runtime

- global patch verification passes;
- profile-local patch verification passes;
- web UI and plugin routes work through the supported gateway path;
- long-lived traffic remains functional;
- terminal/PTTY verification passes where required.

## Security

- authenticated same-origin requests pass;
- unauthenticated requests are denied;
- invalid authentication is denied;
- unexpected `Origin` is denied;
- `Sec-Fetch-Site: cross-site` is denied;
- forged identity assertions on an untrusted/local path are denied.

## Persistence

- production snapshots are required before promotion;
- snapshot completion is machine-checkable;
- candidate tests use copied data;
- rollback tracks both image/source and persistent data where needed.

## Compatibility

- settings read passes;
- safe no-op settings write passes;
- a pre-upgrade session resumes;
- the current model can be re-selected without intentionally changing selection;
- compatibility evidence is recorded in a sanitized report.

## Promotion control

- candidate validation may produce `eligible for manual promotion`;
- no workflow automatically promotes production;
- an operator can identify the exact candidate and exact rollback target before promotion.

# 6. Recommended commit boundaries

Keep implementation commits focused. A recommended sequence is:

```text
Tag v0.1.1 production baseline
Add live authorization smoke tests
Add compatibility report generation
Define downstream snapshot contract
Add candidate upgrade runner
Add upgrade guard integration tests
Watch upstream DSH releases in CI
Document v0.2 production rehearsal
Prepare v0.3 node registry RFCs
```

Avoid combining the entire upgrade guard into one large commit.

# 8. Stop conditions

At any stage, stop and review before continuing when one of the following occurs:

- upstream DSH introduces official functionality that can replace an Orbit compatibility patch;
- authorization boundaries change;
- a DSH release changes persistent-data semantics or migrations;
- historical sessions fail to resume;
- a candidate can only pass by weakening an exact compatibility matcher;
- snapshot/restore guarantees are unclear;
- a proposed feature would require Orbit to own execution behavior that belongs to DSH;
- a proposed automation would make production promotion implicit rather than explicit.

The expected response to these conditions is design review, compatibility-profile revision, or upstream adoption, not bypassing the guard.
