## 2. Global Construction Rules

### 2.1 RFC-First Gate
Before Gate A:
- Documentation and governance contract tests may be updated;
- No v0.7 product runtime implementation may be added under `src/**`, `bin/**`, or `ui/**`;
- RFC-0014 and this SOP may be reviewed and remediated.

After Gate A records GO, product construction may begin.

### 2.2 DSH Boundary
DSH remains an opaque execution runtime on each node.
v0.7 must not encode:
- DSH private frontend component structure;
- private RPC names or cookies;
- direct database mutations inside DSH.

### 2.3 Strict Target Scope & No Bare Wildcards
All stages prohibit:
- executing any fleet job without explicit target node IDs or verified capability selector;
- bare wildcard targets (`"*"`, `"all"`, `"broadcast"`);
- silent drop of target nodes from aggregated results;
- silent failover from an unhealthy node to a healthy peer.

### 2.4 Evidence Honesty
- `PASS` means executed and observed.
- Required but unexecuted work is `NOT_EXECUTED`.
- A failed real run is never overwritten by prose.
- Any post-freeze product or harness fix invalidates the candidate and requires a fresh candidate-bound evidence run.

## 3. Staged Implementation Plan

### Stage 0: Architecture, RFC-0014, and SOP Gate (Gate A)
- **Objective**: Establish the complete design package for fleet workflows, capability-aware scheduling, aggregated results, and auditability.
- **Deliverables**:
  - `docs/rfc/0014-fleet-workflows-and-scheduling.md`
  - `docs/sop/v0.7-fleet-workflows-multistage-sop.md`
  - Acceptance matrix definition (M28 matrix: 28 canonical fields in `scripts/v07-fleet-acceptance-matrix.mjs`)
  - Governance contract tests (`test/v07-governance-contract.test.mjs`)
- **Gate A Review**: Independent architecture review by `@code-reviewer2`. P0/P1/P2 must be 0 for GO.

### Stage 1: Fleet Task Model & Scheduler Core
- **Objective**: Implement fleet task validation, target spec parsing, and core scheduler logic (`FleetJobScheduler`).
- **Scope**:
  - `src/registry/fleet-scheduler.mjs`: `validateFleetTargetSpec`, job state management, capability matching;
  - Unit and contract tests for target validation and capability scheduling.
- **Gate 1 Review**: Independent review of Stage 1 implementation.

### Stage 2: Aggregated Results Collection & Audit Logging
- **Objective**: Implement aggregated results collection, structured execution timeline, and Hub management endpoints (`GET /hub/fleet/jobs`, `POST /hub/fleet/jobs`).
- **Scope**:
  - Hub server endpoints with session and CSRF protection;
  - SQLite audit log recording operator identity, targets, and job metrics;
  - Integration tests for aggregated results and failure containment.
- **Gate 2 Review**: Independent review of Hub endpoints and audit log.

### Stage 3: Operator UI Fleet Workflows View (Gate B)
- **Objective**: Surface Fleet Workflows panel in authenticated operator surface.
- **Scope**:
  - `ui/view-model.mjs` and `ui/app.mjs`: Fleet Workflows tab, job list, trigger dialog;
  - Real-time progress indicators and aggregated summary view;
  - DOM and integration tests for UI dispatch and display.
- **Gate B Review**: UI and end-to-end integration review.

### Stage 4: Outage Containment & Negative Security (Gate 3)
- **Objective**: Prove robust outage containment, target disconnection tolerance, and negative security under concurrent fleet jobs.
- **Scope**:
  - Target node crash during execution marks target failed while peers complete;
  - Reverse node disconnect handling;
  - Zero cross-node credential leakage in task payloads;
  - Integration tests for outage containment.
- **Gate 3 Review**: Negative security and resilience verification.

### Stage 5: Candidate Freeze & Automated Qualification (Gate C)
- **Objective**: Freeze the v0.7 product candidate and execute automated qualification.
- **Scope**:
  - Candidate commit freeze;
  - Automated qualification run producing candidate-bound M28 report (`v07-m28-automated-qualification-<sha>.json`);
  - Mechanical verification of all automated fields.
- **Gate C Review**: Candidate freeze audit and qualification review.

### Stage 6: Mounted Live Evidence, Seven-Artifact Set & Closure (Final Review)
- **Objective**: Execute fresh two-node mounted drill, package seven-artifact release set, create direct-child closure commit, and obtain final review PASS.
- **Scope**:
  - Run-scoped mounted execution with direct and reverse nodes;
  - All 28 M28 fields verified PASS;
  - Packaging canonical seven-artifact release set under `test/evidence/v07/`;
  - Direct-child closure commit on frozen candidate;
  - Independent Final Review by `@code-reviewer2`.

## 5. Stop-Work Matrix

| Symptom | Severity | Required Action |
|---|---|---|
| Bare wildcard accepted without filter | Critical | Stop. Fail closed with `HTTP 400 wildcard-prohibited`. |
| Task dispatched to node lacking capability | Critical | Stop. Reject task or mark skipped. |
| In-flight failure on Node A aborts Node B | Critical | Stop. Enforce failure independence. |
| Product fix required after candidate freeze | Critical | Unfreeze; mint new candidate and execute fresh candidate-bound evidence. |
| Mounted field unexecuted during Stage 5/6 | Blocker | Keep NOT_EXECUTED; never assert or claim unverified PASS. |
| Hygiene, credentials, or runtime residue remaining | Blocker | Clean completely before review submission. |
| Unclean worktree or residue during review | Blocker | Clean completely before review submission. |
| Non-zero P0, P1, or P2 finding | Blocker | Fix, re-test, re-review until PASS. |
