The controlling design documents are:

- RFC-0001 node identity;
- RFC-0005 node enrollment / reenrollment;
- RFC-0006 Registry machine API;
- RFC-0007 browser management API;
- RFC-0008 per-node Hub route identity;
- RFC-0009 health/capability semantics;
- RFC-0010 endpoint/routing model;
- RFC-0011 browser node selection;
- RFC-0012 reverse-connected nodes;

- RFC-0014 fleet workflows and capability-aware scheduling;
- **RFC-0015 scheduled workflows and fleet automation**;
- `V08-CONSTRUCTION-20260926-A1`.

If implementation discovers that any of the following must change, **STOP** and return to architecture review:

- stable `nodeId` semantics;
- deterministic RFC-0010 route authority (`n-<nodeId>.<routeDomain>`);
- strict target scope validation (bare wildcards prohibited);
- delegation of task dispatch to RFC-0014 `FleetJobScheduler`;
- persistent schedule state model in SQLite (`active`, `paused`, `completed`, `error`);
- zero silent cross-node failover;
- independent execution failure containment across nodes;
- the 32-field acceptance matrix in RFC-0015;
- the v0.8 / v0.9 scope boundary.

## 2. Global Construction Rules

### 2.1 RFC-First Gate
Before Gate A:
- Documentation and governance contract tests may be updated;
- No v0.8 product runtime implementation may be added under `src/**`, `bin/**`, or `ui/**`;
- RFC-0015 and this SOP may be reviewed and remediated.

After Gate A records GO, product construction may begin.

### 2.2 DSH Boundary
DSH remains an opaque execution runtime on each node.
v0.8 must not encode:
- DSH private frontend component structure;
- private RPC names or cookies;
- direct database mutations inside DSH.

### 2.3 Strict Target Scope & No Bare Wildcards
All stages prohibit:
- executing any scheduled job without explicit target node IDs or verified capability selector;
- bare wildcard targets (`"*"`, `"all"`, `"broadcast"`);
- silent drop of target nodes from aggregated results;
- silent failover from an unhealthy node to a healthy peer.

### 2.4 Evidence Honesty
- `PASS` means executed and observed.
- Required but unexecuted work is `NOT_EXECUTED`.
- A failed real run is never overwritten by prose.
- Any post-freeze product or harness fix invalidates the candidate and requires a fresh candidate-bound evidence run.

## 3. Staged Implementation Plan

### Stage 0: Architecture, RFC-0015, and SOP Gate (Gate A)
- **Objective**: Establish the complete design package for scheduled workflows, cron/interval triggers, durable execution history, and auditability.
- **Deliverables**:
  - `docs/rfc/0015-scheduled-workflows-and-fleet-automation.md`
  - `docs/sop/v0.8-scheduled-workflows-multistage-sop.md`
  - Acceptance matrix definition (M32 matrix: 32 canonical fields in `scripts/v08-scheduled-acceptance-matrix.mjs`)
  - Governance contract tests (`test/v08-governance-contract.test.mjs`)
- **Gate A Review**: Independent architecture review by `@code-reviewer2`. P0/P1/P2 must be 0 for GO.

### Stage 1: Scheduled Workflow Engine & Cron/Interval Parsing (Gate 1)
- **Objective**: Implement durable schedule models in SQLite schema, cron expression and interval parsing, and `ScheduledWorkflowEngine`.
- **Scope**:
  - `src/registry/sqlite.mjs`: v7 schema migration adding `fleet_schedules` and `fleet_schedule_runs`;
  - `src/registry/schedule-parser.mjs`: 5-field cron parsing, next-run calculations, interval math;
  - `src/registry/schedule-engine.mjs`: `ScheduledWorkflowEngine` lifecycle, periodic evaluation, dispatch delegation to `FleetJobScheduler`;
  - Unit and contract tests.
- **Gate 1 Review**: Independent review of Stage 1 implementation.

### Stage 2: Hub Schedule Management Endpoints & Audit Logging (Gate 2)
- **Objective**: Implement Hub management endpoints (`GET /hub/fleet/schedules`, `POST /hub/fleet/schedules`, pause, resume, trigger, delete) and audit logging.
- **Scope**:
  - Hub server endpoints with session and CSRF protection;
  - SQLite audit log recording operator identity, schedule mutations, triggers, and runs;
  - Integration tests for schedule lifecycle and audit trails.
- **Gate 2 Review**: Independent review of Hub endpoints and audit log.

### Stage 3: Operator UI Scheduled Workflows View (Gate B)
- **Objective**: Surface Scheduled Workflows tab and trigger controls in authenticated operator surface.
- **Scope**:
  - `ui/view-model.mjs` and `ui/app.mjs`: Scheduled Workflows tab, schedule list cards with next-run countdown, schedule creation dialog with cron/interval selector;
  - Execution history modal viewing past scheduled runs;
  - DOM and integration tests.
- **Gate B Review**: UI and end-to-end integration review.

### Stage 4: Resilience, Concurrency & Security (Gate 3)
- **Objective**: Verify concurrency policies (`forbid` vs `allow`), missed-run recovery on Hub restart, and zero credential leakage in schedule configurations.
- **Scope**:
  - Concurrency containment: prevent overlapping runs for slow jobs under `concurrencyPolicy: "forbid"`;
  - Hub restart recovery: deterministic evaluation of missed runs;
  - Zero credential leakage across schedule definitions, payloads, and logs;
  - Resilience and security integration tests.
- **Gate 3 Review**: Negative security and resilience verification.

### Stage 5: Candidate Freeze & Automated Qualification (Gate C)
- **Objective**: Freeze the v0.8 product candidate and execute automated qualification.
- **Scope**:
  - Candidate commit freeze;
  - Automated qualification run producing candidate-bound M32 report (`v08-m32-automated-qualification-<sha>.json`);
  - Mechanical verification of all automated fields.
- **Gate C Review**: Candidate freeze audit and qualification review.

### Stage 6: Mounted Live Evidence, Seven-Artifact Set & Closure (Final Review)
- **Objective**: Execute fresh two-node mounted drill, package seven-artifact release set, create direct-child closure commit, and obtain final review PASS.
- **Scope**:
  - Run-scoped mounted execution with direct and reverse nodes;
  - All 32 M32 fields verified PASS;
  - Packaging canonical seven-artifact release set under `test/evidence/v08/`;
  - Direct-child closure commit on frozen candidate;
  - Independent Final Review by `@code-reviewer2`.

## 5. Stop-Work Matrix

| Symptom | Severity | Required Action |
|---|---|---|
| Bare wildcard accepted without filter | Critical | Stop. Fail closed with `HTTP 400 wildcard-prohibited`. |
| Invalid cron syntax accepted | Critical | Stop. Reject schedule with `HTTP 400 invalid-cron-expression`. |
| Scheduled task dispatched to node lacking capability | Critical | Stop. Mark run skipped or failed without corrupting schedule. |
| In-flight failure on Node A aborts Node B | Critical | Stop. Enforce failure independence. |
| Product fix required after candidate freeze | Critical | Unfreeze; mint new candidate and execute fresh candidate-bound evidence. |
| Mounted field unexecuted during Stage 5/6 | Blocker | Keep NOT_EXECUTED; never assert or claim unverified PASS. |
| Hygiene, credentials, or runtime residue remaining | Blocker | Clean completely before review submission. |
| Unclean worktree or residue during review | Blocker | Clean completely before review submission. |
| Non-zero P0, P1, or P2 finding | Blocker | Fix, re-test, re-review until PASS. |
