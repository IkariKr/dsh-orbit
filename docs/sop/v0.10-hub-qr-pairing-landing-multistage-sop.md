# v0.10 Hub QR Pairing Landing Page Multistage SOP

Status: **Proposed / Stage 0 design package. Product code MUST NOT begin until
RFC-0017 and this SOP receive Architecture Review GO at Gate A.**

Authorization: `V10-CONSTRUCTION-20260928-A1`  
Controlling RFC: `docs/rfc/0017-hub-qr-pairing-landing.md`  
Baseline: `v0.9.0-rc.1` (`145203b8219848796ef627b1f40c0c63233a1d31`)

## 1. Rules of Engagement

- Every stage ends with an **independent code review** (`@code-reviewer` /
  `@code-reviewer2`); the next stage MUST NOT begin until that review records
  an explicit PASS verdict. Review records live in `docs/review/` named
  `YYYY-MM-DD-v10-stageN-<gate>-<sha>.md`.
- Product code is written on stage branches
  (`chore/v010-stage<N>-<slug>`) descending from the governance root; docs
  commits may land on the design branch.
- The **candidate-freeze rule** applies exactly as in v0.9: one frozen
  candidate per evidence round; once frozen, later phases produce only
  qualification/evidence; a real problem means a new candidate and fresh
  candidate-bound evidence.
- Evidence closures are **evidence-only commits** (direct children of the
  frozen candidate) and MUST NOT reference their own SHA.
- Tag/release creation, production promotion, and DNS cutover remain
  separately authorized actions throughout.

## 2. Acceptance Baseline

- Full suite green: `npm run check` (public-tree check + `node --test`),
  zero failures, before any stage gate.
- The M16 matrix (RFC-0017 §3 D7) is the canonical acceptance matrix for
  v0.10. Its 12 automated fields must be mechanically enforced
  (candidate-bound validation, `requirePass: true`); its 4 mounted fields
  must be executed live on the two-node deployment before closure.

## 3. Staged Implementation Plan (Stages 0 through 4)

### Stage 0: RFC-0017, Authorization & SOP Gate (Gate A)

Deliverables:

- `docs/rfc/0017-hub-qr-pairing-landing.md`;
- `docs/release-attestations/v0.10-construction-authorization-2026-09-28.json`
  and `.md`;
- this SOP.

Exit criteria:

- **Gate A Review**: independent architecture review of the design package —
  RFC invariants against the existing registry implementation (host
  classification, fence locations, verify handler, asset serving), scope
  discipline, threat model. GO only.

### Stage 1: Registry `/auth` Surface, Fence Exception & Mint Base Override (Gate 1)

Deliverables:

- `/auth` asset serving on the selector-apex authority (allowlist tuple +
  `selector-authority` meta injection) and the management branch (asset map);
- the D2 fence exception as a total grammar predicate in exactly the two
  affected branches, rejection path byte-identical elsewhere;
- `DSH_ORBIT_HUB_QR_PAIRING_BASE_URL` boot validation (fail-closed exit 1)
  and mint-base override in `/hub/pairing/generate-code` plus
  `hubBaseUrl` in `/hub/pairing/status`;
- `ui/auth/index.html` served (may be a functional stub at this stage);
- mechanical tests for fields A1–A11.

Exit criteria:

- **Gate 1 Review**: independent review of the route/fence/env changes with
  regression focus (A5, A8, A11).

### Stage 2: Landing Page Behavior & Token Hygiene (Gate 2)

Deliverables:

- final `ui/auth/index.html`: state machine (verifying / confirmed / expired
  / invalid / locked / error), address-bar scrub, same-origin verify POST,
  constant first-party success target, referrer/cache headers;
- controller-level tests (Node runner against the exported page logic or a
  thin extracted controller) covering state mapping for A12's failure paths
  and M2/M4 semantics at unit level.

Exit criteria:

- **Gate 2 Review**: independent review of the client behavior and token
  hygiene; zero-leakage assertions reviewed as tests, not prose.

### Stage 3: Resilience, Leakage & Regression Sweep (Gate 3)

Deliverables:

- A12 mechanical leakage scan (audit store + captured responses/logs across a
  full verify round);
- session-cookie attribute regression test (exact v0.9 attributes);
- lockout interplay tests (5 failures ⇒ 15 min lock surfaces as the page's
  `locked` state; `Retry-After` honored);
- full `npm run check` green; public-tree check clean.

Exit criteria:

- **Gate 3 Review**: independent review; candidate freeze readiness.

### Stage 4: Candidate Freeze, Mounted Evidence & Closure (Gate C → Mounted → Final Review)

Deliverables:

- frozen candidate commit (single commit or declared SHA on the release
  branch; freeze recorded);
- fresh candidate-bound automated qualification report (12/12 automated);
- mounted run on the real two-node deployment executing M1–M4 with sanitized
  bindings (candidate SHA, runId, node IDs, TLS/browser provenance), evidence
  under `test/evidence/v10/` with SHA-256/byte manifest;
- evidence-only closure commit (direct child of the frozen candidate):
  `docs/release-attestations/v0.10.0-rc.1.md` + `test/evidence/v10/**` only;
- **Final Review** (P0/P1/P2 = 0 required) closing v0.10 engineering
  acceptance.

Exit criteria:

- Final Review PASS recorded in `docs/review/`.

## 4. Stop-Work Triggers

In addition to the RFC-0017 §5 stop-work matrix: any evidence staleness,
provenance mismatch, cleanup residue, or a review verdict below PASS stops
the wave — a new candidate and fresh evidence are required; no in-place
patching of a frozen candidate.
