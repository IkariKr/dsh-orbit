# v0.3 Registry MVP Multistage SOP

Status: Active (2026-08-31). Baseline: `6786a40` (Registry MVP Phase 1 accepted).
This SOP is the single construction authority for the remaining v0.3 work. Milestone-style free-form development is not authorized; every stage below has fixed scope, outputs, tests, evidence, and stop conditions.

## Scope of authority

- Frozen design authority: RFC-0001/0002/0003/0004/0005/0006/0007/0008/0009 and ADR-0001.
- The Hub side (registry machine API, browser management API, SQLite/WAL persistence, maintenance, health/capability derivation) at baseline `6786a40` is **accepted** and is not subject to refactoring in this plan.
- If implementation finds the SOP insufficient, the change is written back into this document explicitly. Changes touching authentication, identity, trust model, wire protocol, the v0.3/v0.4 scope boundary, or the third-party plugin boundary STOP work and request a design review — never silently adapt.

## Forbidden scope (all stages)

- endpoint selector / traffic routing;
- reverse connection / NAT traversal;
- multi-node sessions;
- fleet execution;
- `terminal.pty` / `agents.run` capability extension;
- any third-party plugin logic, version, path, or compatibility code (ADR-0001).

## Frozen semantics that must never be re-mixed

- `registryContact` is driven by **heartbeat only** (report uploads never touch it).
- Compatibility evidence, capabilities, and `dshHealthy`/`orbitCompatible` are driven by **reports only**.
- A node that receives `401 revoked` from the Hub must **never automatically re-enroll as a new node**; recovery is explicit re-enrollment per Stage 4.

## Uncertain-output principle (applies to Stages 2–4)

Every identity/credential-changing operation must survive uncertain request outcome. Any client-generated material required for an exact replay or commit detection must be persisted **before the request is sent**. Hub commit + lost response + process restart must never orphan the Node identity or leave Hub/local lifecycle states irreconcilable. In particular:

- enrollment: persisted `pendingEnrollment` (requestId + keypair, not the token);
- rotation: persisted `pendingRotation` (old key + pending new keypair); after an uncertain outcome the node probes with the pending new key to detect Hub commit, and never generates a third key "to try again";
- re-enrollment: persisted `pendingReenrollment` (requestId + new keypair) so the same operator token replays the exact request.
- Node local diagnostics must never mutate Hub state: reachability probes are HTTP-level only.

# Stage 2: Node identity + enrollment

**Objective**

Implement the Node Registry Client's local identity: key generation, crash-safe local state persistence, first enrollment, Hub binding, restart recovery, and the failure paths of each.

**Inputs / prerequisites**

- Stage 1 accepted (`6786a40`).
- RFC-0001 (node identity), RFC-0005 D1–D4/D6 (Hub-minted nodeId, digest-only tokens, idempotent enrollment, local persistence), RFC-0006 (enroll route, wire contract).

**Implementation scope**

- Node local store: identity (nodeId), Ed25519 keypair, Hub binding (`hubBaseUrl`), persisted state; atomic/crash-safe writes (temp file + rename), corruption detection.
- Enrollment client: keygen before enrollment; `POST /api/v1/enroll` with operator-provided one-time token + `enrollmentRequestId` + public key; persist issued nodeId/keyId; idempotent retry of the identical request when the response is lost.
- Restart recovery: load persisted identity; never re-enroll an already-enrolled store.
- Failure paths: unknown/expired/consumed token, purpose mismatch, wire violations, network failure during enrollment (leaves store unenrolled; identical retry allowed).

**Required outputs**

- `src/node/store.mjs`, `src/node/client.mjs` (enrollment part), `bin/dsh-orbit-node.mjs` (enroll/status/doctor entry).
- Node state file format documented (schema + fields).

**Required automated tests**

- Store: atomic write, restart recovery, corrupted-file handling.
- Enrollment: success persists identity; identical retry returns same result; failed enrollment leaves no partial identity; explicit refusal to auto-re-enroll an existing store.

**Required live evidence**

- E2E over real loopback HTTP: operator mints token → node enrolls → store file exists with nodeId/keyId → restart (new process instance, same store) → no re-enrollment, identity intact.

**Forbidden scope**

- Reverse connection, multi-node anything, routing, plugins (per global list); also: auto-enrollment without an operator-minted token, enrollment into a nodeId other than the Hub-issued one.

**Failure / stop conditions**

- Any deviation from RFC-0005 D2/D4 (idempotency, digest-only tokens, fresh-nodeId-always rule) requires a stop + design review.

**Stage completion criteria**

- Automated tests green; E2E evidence recorded; store schema stable; no open denial case in the enroll matrix.

# Stage 3: Heartbeat + compatibility report lifecycle

**Objective**

Implement periodic heartbeat with cadence/backoff/jitter, Hub-unavailable detection and automatic recovery, compatibility report generation/upload, and the frozen heartbeat↔registryContact / report↔compatibility-evidence separation.

**Inputs / prerequisites**

- Stage 2 complete.
- RFC-0006 (heartbeat, report-upload routes; runtime identity; transactional nonce), RFC-0009 (registryContact/health semantics; heartbeat runtime identity ↔ report fields 1:1; staleness and recovery).

**Implementation scope**

- Heartbeat loop: default cadence 60s (30–300s configurable), signed ORBIT-MACHINE-V1 requests carrying non-authoritative runtime identity (`orbitVersion`/`orbitRevision`/`dshVersion`/`compatibilityProfile`).
- Failure handling: Hub unavailable / 5xx / 429 → RETRYING with exponential backoff + jitter (cap 60s); recovery to ACTIVE on first success. `401 revoked` → REVOKED state (Stage 4; never auto-re-enroll).
- Report upload: sanitized v0.2 compatibility report upload (schema v2, generated by the existing report pipeline; the node client uploads a provided report); identity must match the heartbeat runtime identity to keep evidence fresh.
- Local runtime state machine: ACTIVE → RETRYING → ACTIVE; ACTIVE stays ACTIVE across transient failures unless revoked.
- Strict separation: heartbeat drives `registryContact` only; report drives compatibility evidence only. The node client never sends capabilities.

**Required outputs**

- `src/node/backoff.mjs`, heartbeat/report in `src/node/client.mjs`, run loop in `bin/dsh-orbit-node.mjs`.

**Required automated tests**

- Backoff: exponential growth, cap, jitter bounds, reset on success.
- Hub unavailable → RETRYING → Hub restored → ACTIVE (real loopback unavailability).
- Report upload derives capabilities at the Hub; revision change → stale; matching fresh report → restored (asserted via Hub state, not node claims).

**Required live evidence**

- E2E chain (loopback): enroll → heartbeat fresh → report → capabilities derived → revision change → stale → fresh report → restored.

**Forbidden scope**

- Node-side capability advertisement or `update-capabilities`-style calls; heartbeat carrying capability state; report uploads affecting `registryContact`.

**Failure / stop conditions**

- Any code path where report upload or heartbeat changes the other dimension (heartbeat↔contact, report↔evidence) outside RFC semantics → stop + design review.

**Stage completion criteria**

- Automated + E2E evidence above green; state machine transitions covered incl. 429/5xx/network/revoked.

# Stage 4: Credential, revocation, and re-enrollment lifecycle

**Objective**

Complete the Node lifecycle: credential rotation with overlap, old-key revocation, Hub delete/revoked handling, explicit re-enrollment, restart during rotation/reenrollment, and Node doctor/status/diagnostics.

**Inputs / prerequisites**

- Stages 2–3 complete.
- RFC-0005 D5 (tombstone, re-enrollment token bound to tombstoned nodeId, original-private-key possession proof, no attestation path), RFC-0006 (credential-rotate with old-key signature + overlap; ORBIT-REENROLL-V1; revoked-key exception confined to reenroll), RFC-0007 (operator mint for both token kinds).

**Implementation scope**

- Node-side rotation: generate new keypair; `POST /api/v1/credential-rotate` signed with the OLD key; overlap window (default 24h) honored; persist new key; rotation marker for diagnostics; restart during rotation resumes with the new key.
- Hub delete handling: heartbeat denied (`401 revoked`) → node enters REVOKED; persists state; **no automatic re-enrollment, no new nodeId**.
- Explicit re-enrollment: operator mints re-enrollment token (`hub.nodes.reenroll`, tombstone-bound); node completes `POST /api/v1/reenroll` with ORBIT-REENROLL-V1 proof signed by the ORIGINAL private key + a NEW keypair; same nodeId restored; old key stays revoked; state ACTIVE.
- Restart during reenrollment: interrupted after completion → store already has restored identity; replay-safe.
- Doctor/status/diagnostics: local store integrity, key/nodeId format checks, hub reachability probe, current state + last events + backoff info; doctor never mutates state.

**Required outputs**

- Rotation/reenroll/revoked handling in `src/node/client.mjs`; `status`/`doctor` output; `bin/dsh-orbit-node.mjs` subcommands.

**Required automated tests**

- Rotation: new key authenticates, old key valid until overlap end, revoked after (Hub-side lazy revocation asserted).
- Revoked handling: 401 → REVOKED persisted; heartbeat retries do NOT auto-enroll (assert no enroll call, state stays revoked, same nodeId kept).
- Re-enrollment: tombstone-bound token; possession proof with original key; same nodeId + new key; old key never regains machine access.
- Restart during rotation and during reenrollment.
- Doctor: reports each integrity class; never fixes.

**Required live evidence**

- Full lifecycle E2E (loopback): fresh node → enroll → persist → restart → heartbeat → report → capability derive → revision change/stale → fresh report → key rotation → old-key revocation (Hub) → Hub delete → machine denial → explicit reenroll → same nodeId + new key → restart recovery.

**Forbidden scope**

- Anything in the global forbidden list; operator-attestation recovery (RFC-0005 D5: none exists); force-rebind mechanics; auto re-enrollment on 401.

**Failure / stop conditions**

- If a real implementation need cannot be met without touching authentication/identity/trust/wire semantics → stop + design review (per scope-of-authority).

**Stage completion criteria**

- All tests green incl. the full lifecycle E2E; doctor/status stable; no auto-recovery path that mints a new nodeId.

**Controlled accelerated aging policy (mounted drill only)**

The RFC-0009 production thresholds are immutable: the default heartbeat
cadence is 60 seconds, three missed beats produce `stale`, and 24 hours
without contact produces `lost` plus `contact-lost`. The mounted Stage 6 drill
MAY use an explicitly enabled, isolated accelerated-aging clock solely for the
Hub's `registryContact` maintenance calculation, so the 24-hour transition can
be tested without waiting 24 wall-clock hours. This is a testability control,
not a production configuration.

The control MUST satisfy all of the following:

- It is accepted only in an explicit drill mode and through a private,
  operator-inaccessible control file or equivalent isolated control plane.
  The mounted drill control is a node-scoped JSON map of `nodeId` to ISO
  timestamps; an unmapped node always falls back to the Hub wall clock, and
  no global future timestamp is permitted. This keeps a live Node B on the
  real heartbeat path while only the disconnected Node A is aged.
- Authentication timestamp validation, real Node heartbeat timers and
  signatures, report upload timestamps, retention, audit timestamps, and all
  other Hub semantics continue to use wall-clock time.
- The unchanged RFC thresholds and both wall-clock and accelerated-clock
  values are recorded in the live evidence.
- The control is reset/removed before reconnect and the final lifecycle
  checks; B continues on the real heartbeat path and must remain fresh.
  Maintenance remains aging-only across the reset: moving the drill clock
  backwards MUST NOT restore `stale`/`lost` to `fresh`; only an authenticated
  heartbeat may restore `registryContact=fresh` and clear `contact-lost`.
- Direct SQLite timestamp edits, changing production cadence/lost constants,
  fake success claims, path canonicalization on the private machine ingress,
  and TLS certificate-validation bypasses are forbidden. The private ingress
  accepts only the exact raw v0.3 machine request-targets and rejects query,
  encoded, dot-segment, browser, and unknown route variants before upstream.

If controlled accelerated aging cannot be implemented with these boundaries,
Stage 6 remains blocked; the production threshold MUST NOT be silently
shortened.

**Forbidden scope**

- Global forbidden list; anything that makes one node's health/credentials affect another.
