## 1. Scope of authority

The controlling design documents are:

- RFC-0001 node identity;
- RFC-0003 node authentication;
- RFC-0005 node enrollment / reenrollment;
- RFC-0006 Registry machine API;
- RFC-0007 browser management API;
- RFC-0008 per-node Hub service identity;
- RFC-0009 health/capability semantics;
- RFC-0010 endpoint/routing model;
- RFC-0011 browser node selection;
- RFC-0012 reverse-connected nodes;
- **RFC-0013 multi-node sessions and target scoping**;
- `docs/sop/verification-tls-trust-policy.md`;
- `V06-CONSTRUCTION-20260925-A1`.

If implementation discovers that any of the following must change, **STOP** and return to architecture review:

- stable `nodeId` semantics;
- deterministic RFC-0010 route authority (`n-<nodeId>.<routeDomain>`);
- strict per-node host-only cookie isolation;
- explicit single-node target scope;
- zero implicit broadcast or cluster-wide command execution;
- zero silent cross-node failover;
- independent per-node resource allocations (reverse channel pools and connection limits);
- the 24-field acceptance matrix in RFC-0013;
- the v0.6 / v0.7 scope boundary.

## 2. Global construction rules

### 2.1 RFC-first gate
Before Gate A:
- documentation/tests validating documentation and governance may be updated;
- no v0.6 product runtime implementation may be added under `src/**`, `bin/**`, `ui/**`, or production gateway configuration;
- RFC-0013 and this SOP may be reviewed and remediated.

After Gate A records GO, product construction may begin.

### 2.2 DSH boundary
DSH remains an opaque execution runtime on each node.
v0.6 must not encode:
- DSH private frontend component structure;
- private RPC names or cookies;
- cluster-wide session synchronization inside DSH.

### 2.3 Strict target scope & no broadcast
All stages prohibit:
- executing any command or routing any flow without an explicit single `nodeId`;
- wildcard targets (`"*"`, `"all"`);
- implicit multi-node dispatch;
- silent failover from an unhealthy node to a healthy peer.

### 2.4 Evidence honesty
- `PASS` means executed and observed.
- Required but unexecuted work is `NOT_EXECUTED`.
- A failed real run is never overwritten by prose.
- Any post-freeze product or harness fix invalidates the candidate and requires a fresh candidate-bound evidence run.

## 3. Staged Implementation Plan

### Stage 0: Architecture, RFC-0013, and SOP Gate (Gate A)
- **Objective**: Establish the complete design package for multi-node sessions, target scoping, UI observability, and isolation invariants.
- **Deliverables**:
  - `docs/rfc/0013-multi-node-sessions-and-target-scope.md`
  - `docs/sop/v0.6-multi-node-sessions-multistage-sop.md`
  - Acceptance matrix definition (M24 matrix: 24 canonical fields)
  - Governance contract tests
- **Gate A Review**: Independent architecture review by `@code-reviewer2`. P0/P1/P2 must be 0 for GO.

### Stage 1: Target Scoping & Hub Flow Tracking Core
- **Objective**: Implement explicit single-node target scope enforcement on management APIs and core flow tracking.
- **Scope**:
  - `MultiNodeFlowTracker` in Hub registry/proxy core;
  - Validation of mandatory single `targetNodeId` on actions;
  - Rejection of wildcard, empty, or multi-target requests;
  - Unit and contract tests for flow accounting and scope enforcement.
- **Gate 1 Review**: Independent review of Stage 1 implementation.

### Stage 2: Hub Read Model & Devices/Nodes View
- **Objective**: Extend Hub overview API and UI view model to surface concurrent node sessions.
- **Scope**:
  - Real-time active flow counts per node in `GET /hub/nodes` and new summary endpoint `GET /hub/overview`;
  - Devices and Nodes view in operator surface (`ui/`);
  - Live presence and reachability indicators without full page refresh;
  - Dedicated scoped launch action per node.
- **Gate 2 Review**: Independent review of UI and read model.

### Stage 3: Concurrent Routing & Resource Partitioning (Gate B)
- **Objective**: Validate concurrent routing through direct and reverse nodes without crosstalk or pool starvation.
- **Scope**:
  - Concurrent HTTP root and static asset requests across Node A (direct) and Node B (reverse);
  - Concurrent WebSocket upgrades and Ping/Pong streams;
  - Partitioned reverse channel pools;
  - Streaming data transfer under multi-node load.
- **Gate B Review**: Multi-node concurrency and security review.

### Stage 4: Outage Containment & Negative Security (Gate 3)
- **Objective**: Prove complete failure isolation between nodes.
- **Scope**:
  - Node A outage / restart while Node B is actively streaming;
  - Node B disconnect while Node A is actively serving;
  - Cross-node route proof replay denial;
  - Cookie jar isolation verification under concurrent multi-node browser access.
- **Gate 3 Review**: Negative security and resilience verification.

### Stage 5: Candidate Freeze & Automated Qualification (Gate C)
- **Objective**: Freeze the v0.6 product candidate and execute automated qualification.
- **Scope**:
  - Candidate commit freeze;
  - Automated qualification run producing candidate-bound qualification report;
  - Verification of all automated fields in the M24 matrix.
- **Gate C Review**: Candidate freeze audit and qualification review.

### Stage 6: Mounted Live Evidence, Seven-Artifact Set & Closure (Final Review)
- **Objective**: Execute fresh two-node mounted drill, package seven-artifact release set, create direct-child closure commit, and obtain final review PASS.
- **Scope**:
  - Run-scoped mounted execution with Node A (direct) and Node B (reverse);
  - All 24 M24 fields verified PASS;
  - Packaging the canonical seven-artifact release set (inherited from v0.5 SOP Section 8.4):
    1. `fresh-install.json`
    2. `migration.json`
    3. `backup-restore.json`
    4. `mounted-runner-raw.json`
    5. `two-node-mounted-smoke.json`
    6. `promotion-plan-validation.json`
    7. `manifest.json` (with LF SHA-256 and byte counts);
  - Direct-child closure commit on frozen candidate;
  - Independent Final Review by `@code-reviewer2`.

## 5. Stop-work matrix

Immediately **STOP** the current stage and request review if any of the following occur:

| Finding | Action |
| --- | --- |
| Need fleet-wide broadcast or batch command execution | architecture blocker; defer to v0.7 |
| Need cross-node cookie sharing or shared domain cookies | security blocker; preserve host-only isolation |
| Need automatic failover from failed node to peer | architecture blocker; fail closed |
| Need generic TCP proxying or general tunneling | architecture blocker; maintain RFC-0010 routing |
| Reverse channel pool shared across nodes | resource blocker; partition pools per node |
| High load on Node B blocks or starves Node A | performance/isolation blocker |
| Product fix required after candidate freeze | unfreeze; new candidate + fresh evidence |
| Mounted field unexecuted | NOT_EXECUTED; no PASS claim |
| Hygiene/residue remaining after run | clean completely before review |
