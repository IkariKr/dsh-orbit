## 2. Stage 5 Objective

Expose the v0.4 browser product experience:

1. the operator enters through one familiar selector authority;
2. the selector shows the registered nodes and their authoritative current route eligibility;
3. the operator explicitly chooses a node;
4. the browser performs a normal full navigation to that node's deterministic route authority;
5. returning to the selector and choosing another node is an explicit action;
6. different tabs may remain on different nodes without any global `activeNode` state.

Stage 5 is a selector, not a fleet dashboard and not a topology editor.

---

## 3. Non-Negotiable Architecture Rules

### 3.1 Selection is represented only by navigation

Do not create any mutable global active-node state in:

- Hub memory;
- Registry DB;
- browser cookies;
- `localStorage` / `sessionStorage`;
- a shared service worker;
- URL-independent frontend state.

An eligible node opens by navigating to:

`<trusted-scheme>://<deterministic-node-authority>/`

The authority must be derived from the RFC-0010 node ID mapping, never from display text.

### 3.2 The server owns eligibility

The browser must not reconstruct the five RFC-0010 eligibility conditions.

The selector UI must consume a server-produced selector read model containing, at minimum:

- authoritative `eligible` boolean;
- stable unavailable reason code when ineligible;
- concise human-readable unavailable reason;
- deterministic `openUrl` only when eligible.

The server must obtain eligibility from the existing `evaluateRouteEligibility()` logic. Do not create a second JavaScript eligibility algorithm.

### 3.3 Preserve the existing Registry management UI

The existing `ui/` application is a management surface containing enrollment token, delete, re-enrollment, route-target administration and node detail behavior.

Do **not** convert that application wholesale into the selector.

Stage 5 should add a dedicated selector bundle, for example:

- `ui/selector/index.html`
- `ui/selector/app.mjs`
- `ui/selector/view-model.mjs`
- `ui/selector/styles.css`

Equivalent file names are acceptable, but the selector and management applications must remain logically separate.

### 3.4 No Registry schema expansion for display names

The current Registry does not persist a v0.4 display-name field.

Stage 5 must therefore display `nodeId` as the row identity fallback and must **not** introduce:

- a display-name migration;
- friendly route aliases;
- user-defined slugs;
- route authority derived from a label.

A future display-name feature can be designed separately. It is not needed to complete Stage 5.

## 4. Required Server-Side Selector Read Model

Add one small server-side selector read-model module rather than teaching the frontend Registry internals. A recommended location is:

`src/registry/selector-view.mjs`

For each Registry node, produce a sanitized selector row with fields equivalent to:

```text
{
  nodeId,
  state,
  runtimeIdentity: {
    orbitVersion,
    dshVersion,
    compatibilityProfile
  },
  health: {
    registryContact,
    reachable,
    orbitCompatible,
    capabilities,
    capabilitiesStale
  },
  route: {
    eligible,
    reasonCode,
    reason,
    openUrl
  }
}
```

Exact JSON property names may differ, but semantics must remain explicit.

The selector response must **not** expose fields the selector does not need, including:

- route-target private/internal origins;
- Hub route-key records;
- enrollment tokens;
- browser sessions;
- audit rows;
- node credential material;
- compatibility report raw JSON.

The selector read model must use:

- `evaluateRouteEligibility(registry, nodeId)` for eligibility;
- `computeRouteAuthority(nodeId, routeDomain)` for deterministic authority;
- the Hub's configured trusted external scheme for `openUrl`.

Do not infer eligibility from a DSH version string.

## 5. Stable Unavailable Reason Mapping

Map the existing server-side eligibility outcomes into selector-facing stable reason codes/messages.

At minimum cover:

| Router eligibility result | Selector reason |
| --- | --- |
| node inactive/tombstoned | node is not active |
| no route target | route target is not configured |
| `reachable = unknown` | route reachability is not verified yet |
| `reachable = unreachable` | route ingress or downstream DSH is unreachable |
| no active Hub route key | Hub route identity is not active |
| compatibility evidence stale | compatibility evidence is stale |
| `web.routes` missing | web routing capability is unavailable |

Keep the raw server reason separate from the concise UI message if useful.

The frontend may render the supplied reason. It must not determine which reason applies.

## 6. Selector Authority HTTP Surface

The selector apex currently serves only a placeholder landing page and rejects `/hub/*`. Stage 5 may intentionally extend that authority, but the extension must be a strict allowlist.

### 6.1 Allowed on selector authority

Serve only:

1. selector static assets;
2. the RFC-0007 session bootstrap/read path needed by the selector;
3. one read-only selector node-list endpoint;
4. optional session logout only if the selector exposes an explicit logout action.

Recommended API shape:

- `POST /hub/session`
- `GET /hub/session`
- `GET /hub/selector/nodes`
- optionally `POST /hub/session/logout`

A different read-only selector path is acceptable if it stays clearly separate from the management mutation surface.

### 6.2 Explicitly forbidden on selector authority

Continue to reject:

- all `/api/v1/*` machine routes;
- token mint/list endpoints;
- node delete/re-enrollment mutations;
- route-target GET/PUT/DELETE administration;
- credential/key administration;
- arbitrary `/hub/*` pass-through.

Do **not** solve Stage 5 by allowing the entire existing management API on the selector authority.

Add host-aware tests proving the allowlist.

## 7. Selector Authentication Boundary

RFC-0011 requires Orbit edge authentication to protect the selector and node route authorities.

The selector data path must preserve the RFC-0007 chain:

1. outer gateway authenticates the operator;
2. outer gateway consumes and strips its own credentials;
3. gateway injects only the internal authenticated-proxy assertion and operator principal;
4. Hub bootstraps a host-only selector session;
5. selector read requests use that Hub session;
6. no gateway credential reaches a Node.

### Required fixture correction for Stage 5

The shared wildcard gateway fixture currently models node-route outer authentication. Before it is used as Stage 5 selector evidence, update it so selector-authority browser/data requests are also protected by the outer authentication gate.

At minimum prove:

- selector request without outer auth -> denied;
- selector request with wrong outer auth -> denied;
- valid outer auth -> selector shell/session/read model works;
- `x-gateway-auth` / equivalent outer credentials are consumed before Hub forwarding;
- client-supplied internal assertion/principal values cannot replace gateway-injected values.

Static assets contain no secrets, but the test topology should still model the accepted production edge-auth boundary rather than accidentally making the selector a public bypass.

## 8. Selector UI Behavior

### 8.1 Row content

Each row must show enough information to answer the v0.4 selection questions without becoming a dashboard:

- node ID;
- active/tombstoned state;
- DSH version;
- Orbit version;
- registry contact;
- reachability;
- compatibility state;
- active `web.routes` status/capability information;
- Open action or concise unavailable reason.

Do not expose internal route-target origins in the selector row.

### 8.2 Open action

Use a real anchor/link for eligible nodes where practical:

```html
<a href="https://n-....example.com/">Open</a>
```

This is preferred over a JavaScript hot swap because it naturally supports:

- full navigation;
- copy link;
- bookmark;
- open in new tab;
- keyboard activation;
- explicit browser-origin visibility.

The href must come from the server read model.

### 8.3 Ineligible nodes remain visible

Never hide an ineligible registered node merely because it cannot currently open.

Show the server-supplied reason instead of an enabled Open link.

### 8.4 Refresh behavior

The selector must have a way to observe current eligibility without deriving it locally.

Acceptable minimal implementation:

- initial fetch;
- explicit Refresh action;
- optional small non-overlapping polling loop.

If polling is implemented, it must only replace the server read model. It must not age health or calculate reachability in JavaScript.

Do not add SSE/WebSocket selector synchronization in Stage 5 unless required by a demonstrated blocker.

## 9. Loading, Empty, Error and Accessibility States

Required states:

- session/bootstrap loading;
- node-list loading;
- zero registered nodes;
- authenticated API failure;
- session expired/re-bootstrap required;
- partial refresh failure without inventing new node state.

Accessibility requirements:

- keyboard-accessible Open and Refresh controls;
- visible focus states;
- status meaning must not depend on color alone;
- loading/error updates exposed through an appropriate live region;
- unavailable reason rendered as text;
- semantic headings/list/table structure as appropriate;
- no click-only non-semantic `div` controls.

Keep the UI small and functional. Stage 5 does not require a visual redesign of the management application.

---

## 10. Node-Unavailable Browser Surface

The existing routed HTTP failure returns a structured `node-unavailable` response with `selectorUrl`. Stage 5 must make the browser return path usable without changing routing semantics.

Required behavior:

- preserve the failed node authority in the address bar;
- never redirect automatically to another node;
- never serve a sibling node under the failed authority;
- offer a visible link back to the selector;
- preserve machine-readable JSON behavior for non-browser callers/tests where already relied upon.

Recommended implementation:

- for ordinary HTTP requests that prefer `text/html`, return a minimal Orbit-owned 503 HTML page containing:
  - selected node ID/authority;
  - concise unavailable reason;
  - selector link;
- retain the structured JSON 503 response for JSON/non-HTML consumers;
- WebSocket non-101 failures remain protocol-appropriate and must not be transformed into an automatic navigation.

Do not introduce cross-node failover.

---

## 11. Direct Bookmark Contract

A deterministic node URL may be opened directly without first loading the selector.

The direct route must still execute the existing server-side eligibility check.

Required tests:

- eligible direct bookmark routes to exactly that node;
- missing/stale `web.routes` -> unavailable;
- `reachable = unreachable` -> unavailable;
- tombstoned node -> unavailable;
- no condition may redirect/fail over to another node;
- browser unavailable surface links back to selector.

The selector is discovery UI, not an authorization bypass.

## 12. Required Automated Test Plan

Stage 5 is not complete until the following classes of tests exist and pass.

### 12.1 Selector read-model unit tests

Add tests covering:

- eligible node -> `eligible=true` + deterministic `openUrl`;
- Open URL is derived from `nodeId`, never label/display text;
- no route target -> stable unavailable reason;
- `reachable=unknown` and `reachable=unreachable` remain distinct;
- stale compatibility evidence -> disabled;
- missing `web.routes` -> disabled;
- tombstoned node -> disabled;
- two nodes produce independent rows;
- selector payload excludes route-target internal origin and Hub route-key records.

### 12.2 Selector authority/server tests

Prove:

- selector assets served only on the selector authority as intended;
- valid RFC-0007 session bootstrap works on selector authority;
- read-only selector endpoint works with authenticated session;
- missing/wrong gateway proof is denied;
- `/api/v1/*` remains denied on selector authority;
- `/hub/tokens*` remains denied;
- route-target mutation remains denied;
- node delete/re-enrollment mutation remains denied;
- unrelated/invalid wildcard hosts remain fail closed.

### 12.3 UI/view-model tests

Prove:

- frontend renders the server eligibility value without recomputing it;
- two independently eligible rows carry different Open hrefs;
- disabling A does not modify B's href/action;
- unavailable reason is visible;
- loading, empty, error and session-refresh states render;
- malicious/textual node values are escaped;
- no global active-node storage is used.

### 12.4 Browser-flow tests

Prove:

- session bootstrap -> selector rows;
- Open is a full navigation target;
- direct bookmark remains server-gated;
- after A becomes `unreachable`, a refresh/poll disables only A;
- stale/missing `web.routes` disables Open without UI version heuristics;
- B remains openable while A is unavailable.

### 12.5 Regression gates

Run at minimum:

```text
node --test <new Stage 5 selector tests>
node --test test/stage3-http-routing.test.mjs test/stage4-websocket-routing.test.mjs
DSH_ACCEPTANCE_ROOT=D:/App/01_Ai/deepseek-harness node --test test/stage4-real-dsh-acceptance.test.mjs
npm run check
```

`git diff --check <Stage5-baseline>..HEAD` must be clean.

No existing Stage 4 route/security test may be deleted or weakened to make Stage 5 pass.

## 13. Required Live Browser Evidence

Before Stage 5 is declared complete, perform a real browser rehearsal against the rehearsal selector/wildcard domain.

Minimum evidence sequence:

1. authenticate through the outer gateway;
2. open the selector authority;
3. verify both Node A and Node B are listed from Registry state;
4. Open A and confirm full navigation to A deterministic authority;
5. open selector in a second tab and Open B;
6. confirm the first tab remains on A and is not retargeted;
7. make A ineligible, preferably by stopping A downstream DSH while ingress remains alive and waiting for the Stage 4 probe threshold;
8. refresh/poll selector and confirm A becomes unavailable while B remains Open-enabled;
9. open/bookmark the now-ineligible A authority and confirm the Orbit-owned failure surface preserves A and links back to selector;
10. restore A and confirm Open returns only after server-side eligibility returns.

Evidence must record:

- exact Orbit SHA;
- browser name/version;
- rehearsal selector authority;
- sanitized A/B node IDs and deterministic authorities;
- which condition made A unavailable;
- expected/actual outcomes.

Do not record:

- cookies;
- gateway credentials;
- CSRF values;
- private keys;
- bearer tokens.

Stage 6 is responsible for the larger mounted two-real-node E2E. Stage 5 evidence proves selector behavior and browser target isolation.

## 14. Explicit Forbidden Scope

Do not implement any of the following in Stage 5:

- global `activeNode` state;
- auto-failover;
- retry-to-another-node behavior;
- iframe embedding of DSH nodes;
- one selector page maintaining live sessions to multiple DSH nodes;
- multi-node command/task execution;
- fleet dashboard metrics expansion;
- topology editor;
- multiple route targets / priority routing;
- friendly DNS aliases or route slugs;
- Registry display-name schema migration;
- DSH cookie parsing or copying;
- DSH launch-token parsing;
- DSH-private RPC knowledge;
- third-party plugin-specific selector logic;
- new WebSocket routing semantics;
- reverse connection / NAT traversal;
- production authority cutover.

If any of these becomes necessary to make the selector work, stop construction and request architecture review rather than expanding scope silently.

---

## 15. Failure / Immediate Stop Conditions

Stop Stage 5 and report the blocker if any of the following occurs:

1. selector requires client-side reconstruction of eligibility;
2. selector requires opening the entire management mutation API on the selector authority;
3. one tab's selection changes another tab without navigation;
4. Open URL cannot be derived solely from node ID + configured route domain/scheme;
5. browser selection requires DSH-private token/cookie parsing;
6. a failed A route is ever served by B;
7. direct bookmark bypasses server eligibility;
8. gateway credentials reach the Node/DSH side;
9. selector work requires Registry schema or identity semantics changes;
10. Stage 4 routing/security tests regress.

Do not patch around an architecture stop condition inside UI code.

---

## 16. Stage 5 Completion Gate

Stage 5 is complete only when all are true:

- selector authority serves the dedicated selector application;
- selector rows come from a sanitized Hub read model;
- server is the only eligibility authority;
- eligible Open URLs are deterministic from node ID;
- ineligible nodes stay visible with concise server-provided reasons;
- outer gateway and Hub session protections apply to selector data;
- selector authority does not expose the management mutation surface;
- direct bookmark behavior remains server-gated;
- browser failure surface links back to selector with no failover;
- two tabs can remain independently on A and B;
- loading/empty/error/accessibility requirements pass;
- required automated tests pass;
- real browser evidence passes;
- full repository `npm run check` passes;
- diff check is clean;
- working tree is clean at reported final HEAD.

At completion, **STOP**.

Do not begin Stage 6 in the same construction batch.

Submit a Stage 5 completion report for independent review. Review must inspect the actual diff and rerun the relevant tests before Stage 6 receives GO.
