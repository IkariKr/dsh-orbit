It is a compatibility qualification record, not a production-promotion record.

### Orbit version metadata clarification

The formal E9 report and `evidence.json` carry the upgrade runner's historical `orbit.version` default, `0.2.0-snapshot`, because `DSH_ORBIT_VERSION` was not explicitly set for the run. That field is optional report metadata; it is not the candidate identity used by the promotion gate.

The qualified executable identity is authoritative by `orbit.revision` `d359a90165ad7bfeeee76d0dd47c2e5212ae6414`. The frozen commit's `package.json` version is `0.4.1-rc.1`. This metadata discrepancy does not change the qualified executable, the snapshot or session inputs, or any E9 check outcomes. It is disclosed here rather than corrected by changing the frozen runner and invalidating the freeze.

The independent Final Review result and formal `verify` result are recorded in this attestation, but their raw stdout transcripts were not retained as standalone repository artifacts. The candidate `report.json` and `evidence.json` remain the machine-verifiable formal E9 artifacts; this retention note does not add or remove a qualification gate.

## Publication decision

E9 is complete for the selected shipping baseline. Orbit `v0.4.1` may therefore publish DSH `0.1.5-rc.2` as `SUPPORTED`, while `0.1.1-rc.2` remains `LEGACY`.

This decision does **not** authorize production promotion of any deployment. A real deployment still requires its own production-data snapshot, rollback target, environment-specific checks, and operator promotion decision. The controlled E9 fixture and its snapshot are release-compatibility evidence only.
