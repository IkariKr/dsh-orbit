## Objective and frozen scope (MUST / SHOULD / OUT)

The objective is roadmap section 0.9 — DSH native plugin integration and QR pairing bootstrap.
This authorization authorizes native DSH plugin packaging under the Cordis framework, Settings service
binding (`~/.dsh/settings.yaml`), ephemeral 6-digit QR pairing bootstrap, DSH desktop settings UI slot
injection, real-time SSE event delivery, and brute-force rate-limiting defense.

**MUST**

- an RFC-first design record (RFC-0016: DSH native plugin integration and QR pairing bootstrap)
  before product construction — no RFC exists yet; it must be written and
  approved via Gate A first;
- standard Cordis plugin packaging (`package.json`, `cordis.patch.yml`) with official entry exports;
- bidirectional configuration binding via DSH Settings service (`~/.dsh/settings.yaml` namespace `dsh-orbit`);
- ephemeral 6-digit pairing codes with <= 300s TTL and single-use destruction on first verification;
- inline vector SVG QR code generation without external network requests or third-party APIs;
- verified TLS enforcement for all remote pairing exchanges and QR links (`https://...`);
- IP rate-limiting and 429 lockout defense against brute-force attacks;
- candidate-freeze rule compliance and fresh candidate-bound evidence for the v0.9 release candidate;
- operator documentation (SOP) and architecture/API reference updates for the DSH plugin.

**SHOULD**

- first-class Orbit Remote & Fleet section in the DSH desktop settings UI via `slots.inject('settings.section')`;
- real-time device connection and pairing events via Server-Sent Events (SSE);
- clear device and node session visibility with one-click revocation.

**OUT OF SCOPE**

- virtual loopback manipulation or rewriting external request Host/Origin/remoteAddress to `127.0.0.1`;
- long-lived 365-day static bearer tokens or unrevocable URL credentials;
- unencrypted HTTP across public or untrusted networks;
- monkey-patching DSH core services (`connection`, `browserAuth`, etc.);
- a new route authority system beyond RFC-0010;
- a new selector system beyond RFC-0011;
- a new DSH compatibility profile without a designed RFC and compliance with the DSH baseline promotion policy;
- unrelated UI refactor;
- unrelated runtime refactor;
- tag or release creation/mutation without separate authorization;
- production promotion without separate authorization;
- DNS cutover without separate authorization.

## Evidence and closure rules

v0.9 construction inherits the evidence and candidate-freeze rules:

1. Exactly one candidate commit is frozen for qualification.
2. Candidate qualification requires executing the 36-field M36 matrix (defined in RFC-0016)
   and producing an automated qualification report (`v09-m36-automated-qualification-<sha>.json`).
3. Stage 6 mounted live evidence requires a fresh, candidate-bound two-node mounted run
   producing the canonical seven-artifact set under `test/evidence/v09/`.
4. The closure commit must be a direct child of the frozen candidate and must not reference
   its own Git SHA.
5. Tagging, production promotion, and DNS cutover remain strictly unauthorized and must not be
   performed as part of engineering acceptance closure.
