# v0.4 Stage 8 Construction Authorization

Authorization ID: `S8-CONSTRUCTION-20260918-A1`
Status: **AUTHORIZED FOR STAGE 8 CONSTRUCTION**
Issued: 2026-09-18

## Authorization decision

Stage 8 construction is explicitly authorized under the bounded scope in this
record. This authorization closes the prior *construction-not-authorized* stop
condition only. It does not retroactively authorize any historical E8.x line,
release/tag action, canonical E9, P3, or production promotion.

The immutable reference points are:

```text
accepted runtime/executable base:
de8eb467a844ef56191f629cdecc6879e561d90a

governance predecessor:
2a1f41a734e0395615ab0ae1ee41173e257a42ec
```

The construction lineage root is the **pushed commit containing this
authorization record**. A new isolated branch/worktree must start from that
remote-exact commit. The future candidate must therefore descend from both the
accepted runtime base and the governance predecessor. The candidate is not
selected by this authorization; it is selected only after authorized
construction is complete and the exact candidate is frozen.

## Authorized Stage 8 scope

The objective is release closure only. Authorized work is limited to:

- creating the new isolated Stage 8 branch/worktree from the pushed
  authorization-record commit;
- reconstructing the minimum non-product evidence harness required to execute
  Stage 8 acceptance;
- release-closing documentation, configuration/SOP, version/changelog and test
  work that stays inside the candidate allowlist;
- freezing one exact candidate;
- running automated, Docker, browser, mounted and evidence-emitter checks
  against that frozen candidate;
- creating a direct evidence-only closure child;
- pushing the candidate and closure for independent Final Review.

Historical E8.3/E8.4/E8.5 work is design/input only. Whole historical Stage 8
commits must not be cherry-picked as construction because those lines contain
product runtime changes that are outside this authorization.

## Candidate allowlist and fail-closed boundary

Candidate construction may modify release-closing docs/tests and only the
explicitly authorized harness/drill files recorded in the machine-readable
authorization JSON. `package.json`/`package-lock.json` may change only for
version metadata; dependency graph changes require an authorization amendment.

The following are product-forbidden in this Stage 8 construction:

```text
src/**
bin/**
ui/**
docker-registry/compose.example.yaml
docker-registry/Caddyfile.example
```

The candidate must not contain:

```text
test/evidence/stage8/**
docs/release-attestations/v0.4.0-rc.x.md
```

If fresh Stage 8 acceptance requires a product runtime/security/identity/trust
change, Stage 8 must stop and return to implementation/security remediation.
This authorization must not be widened implicitly.

## Evidence harness and mounted matrix

The minimum evidence harness may be reconstructed only in the explicitly named
harness/drill paths in the JSON authorization. It must not be used as a vehicle
to transplant historical product changes.

The canonical mounted matrix is frozen to **25 exact fields**. The contract must
validate both count and exact field names from the machine-readable
authorization. Historical prose that said 26 fields is not authoritative.

Every candidate-bound artifact must be generated fresh. Old candidate SHAs,
run IDs, node IDs, browser bindings, TLS fingerprints, timestamps, raw JSON,
hashes, byte counts, or mounted PASS results may not be rebound.

## Two mechanical diff gates

### Governance root -> candidate

The candidate must:

- descend from the pushed authorization-record commit;
- contain no `test/evidence/stage8/**`;
- contain no `docs/release-attestations/v0.4.0-rc.x.md`;
- contain no product-forbidden path;
- stay inside the candidate allowlist.

### Candidate -> evidence closure

The evidence closure must be the candidate's direct child. Its complete changed
path set is restricted to:

```text
docs/release-attestations/v0.4.0-rc.x.md
test/evidence/stage8/**
```

No `src/`, `bin/`, `ui/`, `scripts/`, production configuration, harness or
other path may change in the closure.

The attestation may bind the candidate SHA and runtime base, but it must not
require or predict its own closure Git SHA. The closure SHA is recorded only
after the commit exists by external provenance/reviewer records.

## Run-residue hygiene

Before the evidence closure is committed, generated drill state such as
`data/**`, browser checkpoint files, and unexpected untracked files must be
absent. The closure working tree may contain only the attestation and
`test/evidence/stage8/**`.

## Still not authorized

This authorization does **not** authorize:

```text
v0.5 feature work
reverse connection / NAT traversal
new selector or route mechanisms
new DSH compatibility profiles
product runtime semantic changes
canonical E9
P3
tag/release creation or mutation
production promotion
```

After the evidence-only closure is pushed, Stage 8 must stop at a new
independent Final Review. Tag/release and production promotion each require
separate explicit authorization.
