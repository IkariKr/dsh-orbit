## Objective and frozen scope (MUST / SHOULD / OUT)

The objective is roadmap section 0.6 — multi-node sessions. This authorization
authorizes multi-node session capabilities (concurrent connections to multiple
selected nodes, explicit target scope in the UI, and per-node session isolation).

**MUST**

- an RFC-first design record (RFC-0013: multi-node sessions and target scoping)
  before product construction — no RFC exists yet; it must be written and
  approved via Gate A first;
- concurrent connections to multiple selected nodes across direct and reverse
  transports;
- clear and unambiguous target scope in the UI;
- strict per-node session and cookie isolation (preserving host-only isolation);
- strict prohibition against implicit broadcast execution or silent failover;
- candidate-freeze rule and fresh candidate-bound evidence for the v0.6 release
  candidate;
- operator documentation (SOP) and architecture/configuration reference updates.

**SHOULD**

- first-class Devices and Nodes view in the authenticated operator surface per
  UX reference recommendations (`docs/ux/dsh-remote-mobile.md`);
- per-node session visibility and connection state tracking;
- graceful handling of concurrent node disconnects or reachability degradation.

**OUT OF SCOPE**

- fleet workflows and multi-node batch scheduling (roadmap 0.7);
- a new route authority system beyond RFC-0010;
- a new selector system beyond RFC-0011;
- a new DSH compatibility profile without a designed RFC and compliance with
  the DSH baseline promotion policy;
- unrelated UI refactor;
- unrelated runtime refactor;
- tag or release creation/mutation;
- production promotion;
- DNS cutover.

## Allowed paths

Product and supporting work may touch: `docs/**`, `src/**`, `bin/**`,
`ui/**`, `test/**`, `scripts/**`, `docker-registry/**`, `CHANGELOG.md`,
`README.md`, and `package.json` / `package-lock.json` (dependency changes
require recorded justification). Product construction before RFC-0013 and
Stage 0 Gate A approval is forbidden.

## Forbidden actions

- reopening or rewriting the accepted v0.5 closure lineage or its attestation;
- product construction before RFC-0013 and Stage 0 Gate A approval is recorded;
- changing the DSH baseline outside the DSH baseline promotion policy;
- tag or release creation/mutation, production promotion, or DNS cutover
  without their own separate authorizations.

## Evidence requirements

- Exactly one frozen candidate per evidence round; the candidate must be
  frozen before evidence execution.
- A multi-node session acceptance matrix must be defined in RFC-0013 and
  mechanically enforced by the harness before the v0.6 mounted evidence run.
- One evidence-only closure, a direct child of the frozen candidate; the
  attestation must not reference its own closure SHA.

## Final review and separation of powers

- Independent final review of the v0.6 release candidate and evidence is
  required before v0.6 engineering acceptance.
- Tag/release publication, production promotion, and DNS cutover each remain
  separately authorized actions; none is granted here, and v0.6 construction
  is not gated on them.
