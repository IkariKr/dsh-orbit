## Objective and frozen scope (MUST / SHOULD / OUT)

The objective is roadmap section 0.8 — scheduled workflows and fleet automation. This authorization
authorizes scheduled workflow capabilities (persistent schedule definitions with cron/interval triggers,
deterministic dispatch via FleetJobScheduler, persistent execution history, operator schedule controls,
and auditability).

**MUST**

- an RFC-first design record (RFC-0015: scheduled workflows and fleet automation)
  before product construction — no RFC exists yet; it must be written and
  approved via Gate A first;
- persistent schedule storage in SQLite with atomic status transitions (`active`, `paused`, `completed`, `error`);
- cron expression and interval parsing with timezone pinning and invalid schedule rejection;
- scheduling dispatch delegating strictly to RFC-0014 fleet execution without bypassing target validation;
- missed-run policy handling (skip vs immediate run) and execution window tracking;
- execution history and schedule run logs recording dispatch timeline and results;
- audit logging of schedule creation, pause, resume, mutation, deletion, and dispatch;
- candidate-freeze rule compliance and fresh candidate-bound evidence for the v0.8 release candidate;
- operator documentation (SOP) and architecture/API reference updates for scheduled workflows.

**SHOULD**

- first-class Scheduled Workflows panel in the operator UI with cron schedule inspector and next-run timers;
- real-time schedule trigger status updates;
- schedule execution history inspection modal.

**OUT OF SCOPE**

- a new route authority system beyond RFC-0010;
- a new selector system beyond RFC-0011;
- a new DSH compatibility profile without a designed RFC and compliance with
  the DSH baseline promotion policy;
- distributed external cron daemons;
- unrelated UI refactor;
- unrelated runtime refactor;
- tag or release creation/mutation without separate authorization;
- production promotion without separate authorization;
- DNS cutover without separate authorization.

- reopening or rewriting the accepted v0.7 closure lineage or its attestation;
- product construction before RFC-0015 and Stage 0 Gate A approval is recorded;
- changing the DSH baseline outside the DSH baseline promotion policy;
- tag or release creation/mutation, production promotion, or DNS cutover
  without their own separate authorizations.
