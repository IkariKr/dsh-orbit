## Objective and frozen scope (MUST / SHOULD / OUT)

The objective is roadmap section 0.5 — reverse-connected nodes. This
authorization explicitly authorizes reverse connection / NAT traversal work
as the designed v0.5 goal (roadmap: "the only place reverse connection is
designed"); it is not scope creep when executed inside this record.

**MUST**

- an RFC-first design record for the reverse connection (node-to-hub
  outbound channel, pairing, device authorization) before product
  construction — no RFC exists yet; it must be written and recorded first;
- outbound node-to-hub connection for devices behind NAT or restrictive
  networks;
- pairing and device authorization, distinct from 0.3 server-reachable
  enrollment;
- reconnect and presence handling without requiring a public endpoint per
  device;
- the candidate-freeze rule and fresh candidate-bound evidence for the
  v0.5 release candidate;
- operator documentation (SOP) and architecture/configuration reference
  updates for the new mode.

**SHOULD**

- minimal presence/status surfacing in the existing selector UI so
  reverse-paired nodes are first-class in current views;
- heartbeat/presence integration with the existing contact-aging model;
- deployment and troubleshooting documentation for NAT-restricted
  deployments.

**OUT OF SCOPE**

- a new route authority system beyond RFC-0010;
- a new selector system beyond RFC-0011;
- a new DSH compatibility profile without a designed RFC and compliance
  with the DSH baseline promotion policy;
- unrelated UI refactor;
- unrelated runtime refactor;
- multi-node sessions and fleet workflows (roadmap 0.6 / 0.7);
- tag or release creation/mutation;
- production promotion;
- DNS cutover.

## Allowed paths

Product and supporting work may touch: `docs/**`, `src/**`, `bin/**`,
`ui/**`, `test/**`, `scripts/**`, `docker-registry/**`, `CHANGELOG.md`,
`README.md`, and `package.json` / `package-lock.json` (dependency changes
require recorded justification). Product construction before the
reverse-connection RFC is recorded is forbidden.

## Forbidden actions

- reopening or rewriting the accepted v0.4 closure lineage or its
  attestation;
- cherry-picking quarantined historical constructions into v0.5;
- product construction before the reverse-connection RFC is recorded;
- changing the DSH baseline outside the DSH baseline promotion policy;
- tag or release creation/mutation, production promotion, or DNS cutover
  without their own separate authorizations.

## Evidence requirements

- Exactly one frozen candidate per evidence round; the candidate must be
  frozen before evidence execution. Once a candidate is frozen, later
  phases produce only qualification/evidence; a real problem means a new
  candidate and fresh candidate-bound evidence. An architecture-level
  finding stops for architecture review.
- The v0.5 mounted evidence run must bind, mechanically and current-run
  only: candidate SHA, runId, node IDs, timestamps, browser
  challenge/producer/trust-mode bindings, TLS CA/leaf fingerprints, and the
  seven-artifact set (fresh-install, migration, backup-restore,
  mounted-runner-raw, smoke, promotion-plan-validation, manifest) with
  LF-byte SHA-256 and byte counts. Historical rebinding is forbidden.
- A reverse-connection acceptance matrix must be defined in the RFC and
  mechanically enforced by the harness before the v0.5 mounted evidence
  run.
- One evidence-only closure, a direct child of the frozen candidate; the
  attestation must not reference its own closure SHA; the closure SHA is
  recorded externally after the commit is created.

## Final review and separation of powers

- Independent final review of the v0.5 release candidate and evidence is
  required before v0.5 engineering acceptance.
- Tag/release publication, production promotion, and DNS cutover each
  remain separately authorized actions; none is granted here, and v0.5
  construction is not gated on them.
