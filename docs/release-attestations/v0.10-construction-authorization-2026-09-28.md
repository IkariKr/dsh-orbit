## Objective and frozen scope

The objective is the **hub-hosted QR pairing landing page** — the one
carried-forward product gap recorded in the v0.9 closure: the pairing engine
mints `/auth?token=<code>` URLs, but the registry serves no `/auth` route and
its global query fence rejects every query string, so a scanned QR has nowhere
to land. v0.10 closes exactly that gap. The frozen MUST/SHOULD/OUT scope is in
the JSON record; highlights:

- **MUST** serve `GET /auth` on the selector-apex authority and the management
  (unrelated-host) authority from one shared, self-contained asset set (zero
  external requests). Node-route authorities stay pure proxies.
- **MUST** open a **narrow, fail-closed** exception to the global query fence:
  exactly `GET /auth` with a single `token` parameter matching `^[0-9]{6}$`.
  Every other method/path/parameter combination keeps today's behavior.
- **MUST** add an explicit https-only QR mint base override
  (`DSH_ORBIT_HUB_QR_PAIRING_BASE_URL`, validated at boot) so minted URLs
  resolve on the operator-designated phone-reachable origin. The machine
  pairing env `DSH_ORBIT_HUB_PAIRING_BASE_URL` is **not** repurposed.
- **MUST** enforce token hygiene: address-bar scrub after read, never rendered
  or logged server-side, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`.
- **MUST NOT** invent new credentials, endpoints, or pairing semantics: the
  page consumes the existing `POST /hub/pairing/verify` and its existing
  operator-session bootstrap; post-success navigation is first-party constant
  paths only.
