## Objective and frozen scope (MUST / SHOULD / OUT)

The objective is roadmap section 0.7 — fleet workflows. This authorization
authorizes fleet workflow capabilities (explicit tasks targeting selected nodes,
capability-aware scheduling, aggregated results, and auditability of target
selection and execution scope).

**MUST**

- an RFC-first design record (RFC-0014: fleet workflows and capability-aware scheduling)
  before product construction — no RFC exists yet; it must be written and
  approved via Gate A first;
- explicit tasks targeting selected registered nodes with strict target selection validation;
- capability-aware scheduling matching required capabilities against registered node capabilities;
- aggregated execution results, status summaries, and per-node result collection without silent drop;
- auditability of target selection, execution scope, operator identity, and job timeline;
- candidate-freeze rule compliance and fresh candidate-bound evidence for the v0.7 release candidate;
- operator documentation (SOP) and architecture/API reference updates for fleet workflows.

**SHOULD**

- first-class Fleet Workflows panel in the authenticated operator surface;
- real-time execution progress tracking across target nodes without full-page reloads;
- graceful handling of target node disconnection or outage during job execution.

**OUT OF SCOPE**

- a new route authority system beyond RFC-0010;
- a new selector system beyond RFC-0011;
- a new DSH compatibility profile without a designed RFC and compliance with
  the DSH baseline promotion policy;
- unrelated UI refactor;
- unrelated runtime refactor;
- tag or release creation/mutation without separate authorization;
- production promotion without separate authorization;
- DNS cutover without separate authorization.

## Allowed paths

Product and supporting work may touch: `docs/**`, `src/**`, `bin/**`,
`ui/**`, `test/**`, `scripts/**`, `docker-registry/**`, `CHANGELOG.md`,
`README.md`, and `package.json` / `package-lock.json` (dependency changes
require recorded justification). Product construction before RFC-0014 and
Stage 0 Gate A approval is forbidden.

## Forbidden actions

- reopening or rewriting the accepted v0.6 closure lineage or its attestation;
- product construction before RFC-0014 and Stage 0 Gate A approval is recorded;
- changing the DSH baseline outside the DSH baseline promotion policy;
- tag or release creation/mutation, production promotion, or DNS cutover
  without their own separate authorizations.

## Evidence requirements

- Exactly one frozen candidate per evidence round; the candidate must be
  frozen before evidence execution.
- A dedicated fleet workflow acceptance matrix must be defined in RFC-0014 and
  mechanically enforced by the harness before the v0.7 mounted evidence run.
- One evidence-only closure, a direct child of the frozen candidate; the
  attestation must not reference its own closure SHA.

## Final review and separation of powers

- Independent final review of the v0.7 release candidate and evidence is
  mandatory before v0.7 engineering acceptance can close.
- Release tag creation, public release, production promotion, and DNS cutover
  are separate authorizations.
- Authorizing v0.7 construction does not imply production promotion or DNS
  cutover of earlier releases.
