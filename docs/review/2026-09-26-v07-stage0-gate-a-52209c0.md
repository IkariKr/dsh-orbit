## Findings

### [P1] RFC-0014 D3 fleet-task transport is undefined and conflicts with the frozen RFC-0012 reverse contract and the existing node surfaces

`docs/rfc/0014-fleet-workflows-and-scheduling.md:181-183`

D3 states:

> - Direct nodes are dispatched via HTTP POST to the node's internal task runner or RouteIngress;
> - Reverse nodes are dispatched over dedicated reverse channels using a structured task frame (`mode: "task"`);

Both dispatch paths are unspecified and one directly contradicts a frozen contract:

1. Reverse path conflicts with RFC-0012. RFC-0012 (a controlling document, listed in SOP §1) closes the reverse control vocabulary to `ready` / `status` / ping / pong / close and states "Arbitrary commands, DSH RPCs, shell requests, task execution, browser payload, and fleet messages are forbidden on the control channel" (`docs/rfc/0012-reverse-connected-nodes.md:298`). Its out-of-scope list explicitly names "fleet commands/tasks" and "remote shell/task execution over the control channel" (`docs/rfc/0012-reverse-connected-nodes.md:778-779`). The reverse **data** channel OPEN frame is fixed to `"mode": "http|websocket"` and carries exactly one already-authorized RFC-0010 browser route to the node's local DSH runtime (`docs/rfc/0012-reverse-connected-nodes.md:386`); a fleet task is neither an `http`/`websocket` browser flow nor an RFC-0010 browser route, so `mode: "task"` is a new wire contract with no defined framing, no authorization model (no `routeProof` semantics for a non-browser task), and no bounding rules. The runtime enforces the closed vocabulary today: `src/registry/reverse-session.mjs:174-176` and `src/node/reverse-client.mjs:358-363` hard-close any unknown control type. RFC-0014 depends on RFC-0012 but declares no amendment to it.
2. Direct path cites a component that cannot carry it. `src/node/route-ingress.mjs:1-3` is "Dedicated listener exposing ONLY `GET /_orbit/route-ready` with ORBIT-ROUTE-V1. Rejects all other paths fail-closed without forwarding to upstream DSH." It cannot accept a task POST, and no "internal task runner" exists anywhere under `src/**`. So D3's direct dispatch has no host surface, and no task-dispatch authentication/authorization model is defined for either transport.

Impact: the Stage 0 Gate A deliverable is the frozen transport contract. As written, Stage 1-4 construction would either have to violate the frozen RFC-0012 wire contract or invent an unspecified task frame/endpoint (framing, auth, bounding, audit), which is exactly what Gate A is supposed to pin down. Trigger: any attempt to implement D3 as written.

Minimum fix direction: either (a) explicitly amend RFC-0012 (new reverse data-channel frame type `mode: "task"` with its own framing, authorization, and bounding, and remove `fleet commands/tasks` from the RFC-0012 out-of-scope list as an approved v0.7 extension), or (b) redesign the reverse dispatch transport; and define the direct-node task endpoint (path, auth via ORBIT-ROUTE-V1 or node identity, bounding) rather than citing RouteIngress, which rejects it. This must be resolved before Gate A GO.

### [P2] D5 names a non-existent audit table and column

`docs/rfc/0014-fleet-workflows-and-scheduling.md:198-201`

D5 requires fleet job records to be "recorded in the Hub's SQLite `audit_log`" with fields `action`, `actor`, and `metadata`. The actual durable audit store is the `audit` table with columns `id, at, actor, action, detail_json` (`src/registry/sqlite.mjs:760`, column list at `src/registry/sqlite.mjs:88`), written via `INSERT INTO audit (at, actor, action, detail_json)` (`src/registry/registry.mjs:333-336`). There is no `audit_log` table and no `metadata` column.

Impact: an implementer following the RFC literally would create a second `audit_log` table, splitting the audit trail from the existing `audit` store. Acceptance field 25 `auditLogQueryFiltering` ("queries by jobId, operator, or time range return complete history") and field 8 `fleetJobAuditLogRecorded` then cannot be satisfied against one log. Trigger: implementation of D5 as written. Minimum fix: name the existing `audit` table / `detail_json` column (or explicitly authorize a new table in an amended design), and rename the D5 `metadata` field to `detail_json`.

### [P2] D6 self-contradicts the M28 field split

`docs/rfc/0014-fleet-workflows-and-scheduling.md:59`

D6 says the 28-field matrix is enforced across "automated qualification (9 fields) and live mounted drill runs (19 fields)". The authoritative matrix defines 13 automated + 15 mounted, and the governance test asserts exactly that (`scripts/v07-fleet-acceptance-matrix.mjs:5-32`, `test/v07-governance-contract.test.mjs:127-128`).

Impact: the RFC states two mutually exclusive field accounting splits within the same document; any qualification/evidence accounting derived from the prose (9/19) will disagree with the mechanical matrix (13/15) and the Stage 5/6 evidence set. Trigger: any reader/implementer using line 59 as the split. Minimum fix: correct line 59 to "13 automated / 15 mounted".

### [P3] D2 reference implementation does not match the real registry read models

`docs/rfc/0014-fleet-workflows-and-scheduling.md:154-159`

D2 capability mode uses `registry.listNodes().filter((n) => n.state === "active")` and then `JSON.parse(n.capabilities || "[]")`, `n.capabilities_stale === 0`, `n.node_id`. The real `listNodes()` maps rows through `toNodeSummary` (`src/registry/registry.mjs:1384-1386`), whose shape is `{ nodeId, state, routeMode, health: { capabilities, capabilityEvidence, capabilitiesStale, ... }, ... }` (`src/registry/registry.mjs:1409+`): there is no top-level `node_id`, `capabilities`, or `capabilities_stale`. Only `getNodeRow()` returns raw snake_case rows (`src/registry/registry.mjs:314`), which D2 uses for explicit mode. So D2 mixes raw-row and summary shapes inconsistently. Additionally, `toNodeSummary` already withholds capabilities when stale (`capabilities: []` if `capabilities_stale === 1`), so filtering a summary on `capabilities_stale` is redundant and the raw `JSON.parse(n.capabilities || "[]")` silently yields `[]`, returning `empty-target-set` (fails closed, but functionally wrong).

Secondary: the guard `targetSpec === "*"` at `docs/rfc/0014-fleet-workflows-and-scheduling.md:126` is unreachable because a bare-string `"*"` is rejected earlier by the object-type guard and returns `invalid-target-spec`, not the `wildcard-prohibited` code that acceptance field 4 expects.

Impact: the reference code cannot be implemented as written and produces a different failure code than the acceptance matrix expects. Trigger: literal transcription into `src/registry/fleet-scheduler.mjs` (Stage 1). Minimum fix: pin D2 to one read model (raw rows via `getNodeRow`/an explicit node-row query) and align the wildcard code path with field 4.

### [P3] D1/D4 per-node status vocabulary is inconsistent with the summary counters and the acceptance matrix

`docs/rfc/0014-fleet-workflows-and-scheduling.md:88-90`, `:96-99`, `:186-187`

`NodeTaskStatus` has seven values (`pending, running, completed, failed, timeout, unreachable, skipped`) but the `summary` object counts only `totalTargets, completed, failed, skipped, timeout` — no `unreachable` (and no `pending/running`). Acceptance field 17 `targetNodeOutageDuringJobExecution` says a Node A crash "marks Node A failed", while D4/field 18 assign a disconnect to `unreachable`; the crash-vs-disconnect status mapping (`failed` vs `unreachable`) is therefore ambiguous.

Impact: the D4 completeness invariant is on `Object.keys(results)` so no silent drop occurs, but `summary` cannot account for an `unreachable` node, and the crash status is undefined between D4 and field 17. Trigger: Stage 2 aggregation and Stage 4 outage evidence. Minimum fix: add an `unreachable` counter (or define a total reconciliation), and fix the crash→status mapping consistently across D1/D4/field 17.

### [P3] Stop-Work matrix omits the post-freeze invalidation row

`docs/sop/v0.7-fleet-workflows-multistage-sop.md:167-176`

The v0.7 Stop-Work matrix has 5 rows and omits "any post-freeze product/harness fix invalidates the candidate and requires fresh candidate-bound evidence" and "mounted field unexecuted → NOT_EXECUTED, no PASS claim". These are stated in §2.4 Evidence Honesty but not surfaced in the stop-work table, unlike the v0.6 matrix which carried equivalent rows (`docs/sop/v0.6-multi-node-sessions-multistage-sop.md:182+`).

Impact: a stage owner scanning only the stop-work matrix could miss the candidate-invalidation trigger during Stage 5/6. Trigger: post-freeze fix without re-freeze. Minimum fix: add the freeze-invalidation and unexecuted-mounted-field rows to the matrix.

## Residual Risks

- `generateM28AutomatedQualificationMatrix()` sets all 13 automated fields to PASS unconditionally (`scripts/v07-fleet-acceptance-matrix.mjs:143-149`) with no binding to executed test results. This mirrors the accepted v0.6 M24 prior art, but it means the "automated qualification" PASS set is only as trustworthy as whatever Stage 5 wires into it; the generator itself provides no evidence honesty guarantee.
- `assertM28MatrixShape(..., { scope: "mounted" })` validates mounted fields as PASS but does not require the 13 automated fields to be PASS, so a mounted-scope candidate-bound report can be validated with automated fields still `NOT_EXECUTED`. Identical to accepted v0.6 M24 behavior, so treated as prior-art residual risk rather than a new finding.
- RFC-0014 D3 leaves `maxConcurrentDispatches` (default 8) and the per-task timeout (default 30s) without any relationship to the RFC-0012 reverse data-channel pool bounds (one flow per channel, 2s capacity wait, `reverse-capacity` 503). Concurrent fleet dispatch on reverse nodes may exhaust the pool in ways D3 does not describe.
- Whether the SOP's Gate A/1/2/B/3/C naming and the "P0/P1/P2 must be 0 for GO" bar are intentionally carried forward from v0.6 (they match v0.5/v0.6 prior art) is assumed consistent; not re-litigated here.
