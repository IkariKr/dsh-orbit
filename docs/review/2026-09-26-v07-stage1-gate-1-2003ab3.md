## Findings

### [P1] Job cancellation does not abort in-flight dispatch; the cancelled node is resurrected as `completed` and the summary invariant is corrupted

`src/registry/fleet-scheduler.mjs:225`, `:344-389`, `:405-428`, `:514-531`

`cancelJob()` aborts the `AbortController`, sets `job.status = "failed"`, and marks every `pending`/`running` node result `failed` (`summary.failed++`). But the abort signal is never propagated into the dispatch: `dispatchTransport` is called without any `AbortSignal` (`:448-455`), and the worker's `dispatchNext` continues running to settlement. When the in-flight dispatch resolves, `dispatchNext` unconditionally overwrites the node result (`nodeTask.status = result.status`, `:364`) and increments the success bucket (`job.summary.completed++`, `:372-380`) **on top of** the `failed` count that `cancelJob` already recorded. Step C then sets `job.status = "completed"` because `completed === totalTargets` (`:405-406`), and the accounting-invariant check at `:414-425` throws — but that throw is swallowed by `.catch(() => {})` at `:225`, so the corrupted state is the final, observable state.

Reproduced (500 ms transport, cancel immediately after `submitJob`):

- Immediately after `cancelJob`: `status:"failed"`, `results[A].status:"failed"`, `error.code:"job-cancelled"` (the state the test asserts).
- After the in-flight dispatch settles: `status:"completed"`, `summary:{totalTargets:1, completed:1, failed:1, skipped:0, timeout:0, unreachable:0}`, `results[A]:{status:"completed", error:{code:"job-cancelled"}, exitCode:0}`.

Impact: an operator who cancels an in-flight job (M28 field 26 `fleetJobCancellation`) is shown the job as **completed**, the cancelled node reported `completed` with a contradictory residual `job-cancelled` error, and the D4 reconciliation invariant `totalTargets === completed + failed + skipped + timeout + unreachable` (RFC-0014 D4 / §3 D1) is violated (`1 !== 2`) in the final snapshot. The reconciliation guard that should catch this is defeated because the executor's promise rejection is discarded.

Trigger: any `cancelJob()` issued while at least one dispatch is in flight (the normal cancellation case). Deterministic, not a rare race.

Minimal fix direction: pass an abort signal into `dispatchWithTimeout`/`dispatchTransport` and have `dispatchNext` (a) check `signal.aborted` after `await` before mutating the node result/summary, and (b) not double-count outcomes already recorded by `cancelJob`; and stop swallowing the invariant violation silently (surface it, or mark the job failed rather than leaving a bogus terminal status).

### [P2] `getJob` / `listJobs` snapshots are shallow copies; nested payload, result, and targetSpec objects remain shared with live scheduler state

`src/registry/fleet-scheduler.mjs:239-254`

`getJob` spreads one level only: `payload: { ...job.payload }` (`:242`), `targetSpec: { ...job.targetSpec }` (`:243`), and `results: ... map(([k,v]) => [k, { ...v }])` (`:251-253`). Nested objects and arrays are shared by reference with the internal job. Reproduced:

- `snap.payload.nested.deep = 999` → internal `job.payload.nested.deep` becomes `999` (the internal payload observed via a later `getJob` returns `{"nested":{"deep":999}}`).
- `snap.results[A].error.code = "mutated"` → the next `getJob` returns `error.code:"mutated"`.
- `snap.targetSpec.nodeIds.length = 0` → internal `job.targetSpec.nodeIds` becomes `[]`.

Impact: `getJob`/`listJobs` are documented as "immutable snapshot" (`:231`, `:258`) and back M28 field 1 `fleetJobListObservability`; any consumer (Stage 2 `GET /hub/fleet/jobs` handlers, UI view models, tests) that mutates a returned snapshot silently corrupts the scheduler's canonical state and future reads. The `targetSpec` case is the most damaging because the audit record (RFC-0014 D5) is derived from it. This is a real contract violation with limited reachability today (Stage 2 serializes to JSON read-only), hence P2.

Trigger: any in-process consumer that mutates a field of the returned snapshot beyond the first level.

Minimal fix direction: deep-clone the mutable sub-structures (e.g. `structuredClone` on `payload`/`targetSpec`/`results`, or clone `targetSpec.nodeIds` and each result's `error`), or return frozen snapshots.

### [P2] Capability filter fails open when the registry row is unavailable — `requiredCapabilities` is not enforced

`src/registry/fleet-scheduler.mjs:297-335` (specifically the `if (this.registry)` guard at `:301` and the `if (row)` branch at `:303` with no `else`)

In Step A, `isEligible` starts `true`. Capability enforcement only runs when `this.registry` is truthy **and** `getNodeRow(nodeId)` returns a truthy row. If the registry is absent, lacks `getNodeRow`, or returns no row for the node, the entire capability check is skipped and the node is dispatched as eligible. Reproduced: a scheduler with a registry exposing `listNodes` but returning `null` from `getNodeRow`, a node whose stored capabilities do not include the required capability, and `requiredCapabilities:["package-audit"]` → the node **is** dispatched (`dispatchTransport` invoked) and the job reports `status:"completed", completed:1`.

Impact: violates RFC-0014 D3.1 ("Node must possess all `requiredCapabilities` … Nodes with stale evidence are excluded") and the SOP Stop-Work row "Task dispatched to node lacking capability | Critical | Stop." A missing/unavailable capability row is treated as "capable" rather than "fail closed", so a node with unknown capabilities is dispatched instead of `skipped`.

Trigger: registry row unavailable at execution time — a scheduler constructed without a registry, a registry without `getNodeRow`, or a node deleted/tombstoned between validation and execution (TOCTOU). Reachability is bounded because explicit-target validation normally guarantees the row exists, hence P2 rather than P1.

Minimal fix direction: treat an unresolvable row as ineligible (fail closed) — e.g. `if (!row) { isEligible = false; skipReason = "capability-evidence-stale"; }` — instead of leaving `isEligible` untouched.

### [P2] Timed-out (and cancelled) dispatches are never aborted — no cancellation signal reaches the transport

`src/registry/fleet-scheduler.mjs:436-462`, `:448-455`, `:344-401`

`dispatchWithTimeout` races the dispatch against a timeout `Promise`, but when the timeout wins, the losing dispatch promise is neither aborted nor awaited — the underlying node task keeps running (no `AbortSignal` is passed to `dispatchTransport`). RFC-0014 D3.4 requires the opposite: "If Node A exceeds the timeout, the Hub marks Node A `status:"timeout"` **and aborts its channel** (`type:"abort", code:"task-timeout"`)". Because the scheduler core owns dispatch and provides no abort hook, Stage 2/4 cannot implement the required channel abort without changing this interface.

Impact: a node whose task exceeded its timeout continues executing the cancelled work (resource leak / unbounded side effects on the node), and the same missing signal is the root cause of the P1 cancellation corruption. Not a functional-status regression today (timeout status is recorded correctly and peers are unaffected — field 9 verified), hence P2.

Trigger: any dispatch that exceeds `timeoutMs`, or any `cancelJob()` while a dispatch is in flight.

Minimal fix direction: create a per-node `AbortController` (linked to the job controller), pass its `signal` to `dispatchTransport`, and abort it on timeout; have the transport honor it.

### [P3] Test coverage gap: the cancellation test asserts only the pre-settlement snapshot and misses the P1 race

`test/v07-stage1-fleet-scheduler.test.mjs:382-409`

The "cancellation aborts in-flight tasks cleanly (field 26)" test cancels a 500 ms dispatch and immediately asserts the snapshot (`:405-408`) without awaiting `_executionPromise` or asserting the settled state. It therefore passes while the actual post-settlement state is corrupt (see P1). There is likewise no test asserting snapshot immutability for nested fields (P2), no test for the missing-row capability path (P2), and the timeout test (`:281-341`) does not assert that the slow dispatch was aborted.

Impact: the suite gives false confidence on field 26 and on the D4 invariant, which are the exact behaviours Stage 1 must guarantee.

Minimal fix direction: after cancellation, `await` the execution promise and assert the terminal status and the accounting invariant; add negative cases for the fail-open and immutability paths.

- The M28 automated fields are still asserted PASS unconditionally by `generateM28AutomatedQualificationMatrix()` with no binding to executed test results (accepted v0.6 M24 prior art). Stage 1 does not change this; it remains a Stage 5 evidence-honesty dependency.

This is consistent with the documented idempotency intent (field 11) and is not raised as a finding, but it can mask client errors and drop a second operator intent from the audit trail in Stage 2.
- The 6 skipped tests in the full suite were not individually enumerated; they are pre-existing and unrelated to this diff (the new file contributes 9 passing tests).
