## Findings

### [P0] `GET /hub/audit` and `POST /hub/audit/query` expose live session IDs, enabling cross-operator session hijack

`src/registry/server.mjs:764-765`, `src/registry/server.mjs:823-829`, `src/registry/registry.mjs:339-370`, `src/registry/registry.mjs:1517/1539/1711`, `src/registry/server.mjs:646-653`

`Registry.queryAudit` returns the raw `detail_json` for every audit row, and the two new endpoints return that table (up to `limit`) to **any** authenticated operator without any operator scoping or field redaction. The audit table stores the **live session identifier** in `detail.sessionId` for `session.bootstrap` (`registry.mjs:1517`), `session.logout` (`:1539`), and `session.expired` (`:1711`).

That identifier is the bearer credential: the session cookie value is exactly the session ID (`SESSION_COOKIE = "dsh-orbit-hub-session"`), and `validateSession` (`registry.mjs:1522-1532`) resolves a request purely by `session_id` lookup — it performs no check that the gateway-injected principal matches the session's `operator_principal`. `validateSessionOnly` (`server.mjs:646-653`) trusts the cookie alone.

Trigger and impact (reproduced independently, two distinct operators):

1. Attacker `op-attacker` bootstraps its own session (legitimate gateway admission).
2. `POST /hub/audit/query {operator:"op-victim", action:"session.bootstrap"}` (or `GET /hub/audit`) returns `op-victim`'s `detail.sessionId`.
3. Attacker sends that session ID as the `dsh-orbit-hub-session` cookie. `GET /hub/session` returns `{"principal":"op-victim", ...}` with a **fresh valid CSRF token**, even though the gateway-injected principal is still `op-attacker`.
4. Attacker performs CSRF-protected mutations as the victim — confirmed by minting an enrollment token (`POST /hub/tokens`) as `op-victim` (HTTP 200, token issued).

Observed:

```
harvested: op-victim=sess_60044c... | op-attacker=sess_fbbc6b...
injected principal=op-attacker, stolen cookie -> authenticated as: op-victim (status 200)
mutation as victim: 200 {"tokenId":"etok_12eceb6abf80355c","token":"e88a69084301df5e6826e868b501596a",...}
```

This is a complete authentication bypass / privilege escalation between operator identities, and it directly contradicts RFC-0007 ("Hub sessions ... bind to the gateway-verified operator identity only"; session events are audit records *attributed* to the principal). Before this commit no HTTP surface returned audit rows (`528218c` has no `/hub/audit` route and no `queryAudit`), so the confidentiality break is introduced by this diff; the underlying "cookie value == session ID, no principal rebinding" weakness is pre-existing but was not remotely reachable.

Minimal fix direction: do not return raw `detail_json` from a management read surface — whitelist returned fields per action and redact `sessionId` (and any other credential-like value) before serialization; and/or scope audit reads to a privileged operator. Independently, `validateSessionOnly` should reject a session whose `operatorPrincipal` differs from the gateway-injected principal.

### [P1] Fleet job `payload` and node `stdout`/`stderr` are returned unscrubbed to every operator

`src/registry/server.mjs:746-758`, `src/registry/fleet-scheduler.mjs:295-312` (`getJob`)

`GET /hub/fleet/jobs` and `GET /hub/fleet/jobs/:jobId` return the full job snapshot including `payload` and per-node `stdout`/`stderr`, with no operator scoping and no scrubbing. Any authenticated operator can read any other operator's job payload. Reproduced with two operators:

```
bob sees alice job payload: {"apiKey":"sk-live-SUPERSECRET","password":"hunter2"}
bob reads alice job detail payload: {"apiKey":"sk-live-SUPERSECRET","password":"hunter2"}
```

RFC-0014 D5 requires "Zero credential leakage: task payloads and output logs scrub tokens, private keys, and session cookies." No scrubbing is implemented anywhere in the dispatch, aggregation, or read path. The SOP §2.3 also prohibits silent scope widening. Trigger: any two authenticated operators (the config's `operatorPrincipal.mode:"inject"` and the test suite's own `operator-alice`/`operator-bob` principals treat operators as distinct identities).

Minimal fix direction: scrub credential-shaped values from `payload`/`stdout`/`stderr` before returning them, and/or restrict job visibility to the submitting `operatorPrincipal` (or a privileged role).

### [P2] `POST /hub/audit/query` returns HTTP 500 `internal-error` for malformed filter values

`src/registry/registry.mjs:339-370`, `src/registry/server.mjs:823-829`

`queryAudit` binds caller-supplied `jobId` / `operator` / `action` / `since` / `until` / `limit` directly into SQLite without type validation. Non-primitive or non-integer values raise a driver error that propagates through `sendError` to a 500. Reproduced:

```
audit/query {"jobId":{}}   -> 500 internal-error   (Unknown named parameter '0')
audit/query {"jobId":["a"]}-> 500 internal-error
audit/query {"action":{}}  -> 500 internal-error   (datatype mismatch)
audit/query {"since":{}}   -> 500 internal-error
audit/query {"until":[]}   -> 500 internal-error
audit/query {"limit":10.5} -> 500 internal-error
audit/query body=null      -> 500 internal-error
```

This violates the transport's own stated invariant (`server.mjs:4` "5xx-never-allowed"; RFC-0007 security matrix "5xx upstream | failed case (never allowed)") and is client-triggerable with a valid session+CSRF. No SQL injection was found — all values are parameterized — so impact is limited to the incorrect status code, console error noise, and the broken never-5xx contract.

Minimal fix direction: validate/coerce each filter to its expected primitive type (string for `jobId`/`operator`/`action`/`since`/`until`, integer for `limit`) and return 400 `bad-request` on mismatch, before the SQL call.

### [P2] Cancel on a terminal job returns a misleading `200 {ok:true, status:"failed"}` without changing state

`src/registry/server.mjs:808-820`

The handler fetches the job, confirms it exists, then calls `cancelJob(jobId)`. `FleetJobScheduler.cancelJob` (`fleet-scheduler.mjs:605-627`) returns `false` for an already-terminal job, but the handler ignores the return value and unconditionally replies `{ ok: true, jobId, status: "failed" }` with HTTP 200 (and writes no `fleet.job.abort` audit row). Reproduced:

```
status before cancel: completed
cancel response: 200 {"ok":true,"jobId":"job_9052da...","status":"failed"}
actual job status after cancel attempt: completed
audit actions: fleet.job.complete,fleet.job.create
```

Impact: the operator surface is told the job is `failed` when it actually `completed`; any consumer trusting this response records a false terminal state. This undermines M28 field 26 (`fleetJobCancellation`) evidence integrity.

Minimal fix direction: branch on the `cancelJob` return — on `false`, return 409 `conflict` with the real current `status`; only report `status:"failed"` when the cancel actually took effect.

### [P2] Duplicate `jobId` re-submission writes a duplicate `fleet.job.create` audit row

`src/registry/server.mjs:793-799`

`submitJob` is idempotent on an existing `jobId` and returns the original job snapshot (`fleet-scheduler.mjs:190-193`), correctly avoiding duplicate execution. However the handler then records `fleet.job.create` **unconditionally**, so a replay of the same `jobId` appends a second create row for one job. Reproduced:

```
audit actions for dup job: fleet.job.create, fleet.job.complete, fleet.job.create
```

Impact: the authoritative audit table (RFC-0014 D5, M28 field 8) is polluted — a single fleet job produces two `fleet.job.create` records, so audit counting/attribution by `jobId` double-counts. Field 25's "complete history" is thus not a faithful creation record.

Minimal fix direction: only record `fleet.job.create` when the submission actually created a new job (e.g. have `submitJob` report `created: true/false`, or pre-check `fleetScheduler.getJob(body.jobId)` before recording).

### [P3] Audit-write failures are silently swallowed and are not transactional with the job mutation

`src/registry/fleet-scheduler.mjs:508-510`, `src/registry/server.mjs:1017-1034`, `src/registry/server.mjs:793-799`

The `onJobCompleted` invocation and the `fleet.job.complete` callback both wrap `recordAudit` in `try { ... } catch {}`, discarding any error. RFC-0014 D5 states "Every fleet job execution writes directly to the Hub's authoritative SQLite audit table." Unlike the session-mutation precedent (`test/registry-admin-api.test.mjs:611` requires a failed audit to leave no session row), a failed fleet audit is invisible: the job runs and completes with no error surfaced and no durable record. `fleet.job.create` is likewise not in a transaction with `submitJob` (execution has already started asynchronously before the audit insert).

Impact: M28 field 8 audit completeness can silently fail. Fail-safe (no corruption), but the failure is unobservable.

Minimal fix direction: at minimum log swallowed audit errors; ideally record the create audit inside the submission critical section and surface/report completion-audit failures.

### [P3] New fleet job paths replicate the malformed-percent-encoding 500, and job-scoped audit returns 200 for unknown jobs

`src/registry/server.mjs:751`, `:760`, `:808`

The new routes call `decodeURIComponent` on the raw path segment without a try/catch, replicating the pre-existing pattern at `:720/:734/:878/:898/:948`. Reproduced: `GET /hub/fleet/jobs/%ZZ`, `GET /hub/fleet/jobs/%ZZ/audit`, and `POST /hub/fleet/jobs/%ZZ/cancel` all return `500 internal-error` (URIError). Separately, `GET /hub/fleet/jobs/:jobId/audit` returns `200 {"audit":[]}` for a non-existent job rather than 404, so a caller cannot distinguish "unknown job" from "job with no audit rows".

Impact: low (wrong status codes only; the class is pre-existing and not introduced here, but Stage 2 adds three new instances). Minimal fix direction: guard `decodeURIComponent` (or 400 on malformed encoding) and 404 unknown `jobId` in the job-audit route.

## Residual Risks

- The P0 hijack depends on the pre-existing "session cookie value == session ID, no principal rebinding" design. Even after redacting `sessionId` from audit output, that design remains a latent risk if any other surface ever discloses a session ID (e.g. logs, future read models); the principal-rebinding check in `validateSessionOnly` is the durable defense and is currently absent.
- Whether cross-operator job/audit visibility is intended for this deployment is not stated in RFC-0014 or the SOP; the P1/P0 findings assume the multi-operator model that RFC-0007 and the test suite's distinct principals imply. If the product is strictly single-operator, the cross-operator impact narrows — but the P0 hijack and the RFC-0014 D5 no-credential requirement still hold.
- M28 automated fields are asserted by tests; the matrix's automated PASS binding to executed results is unchanged by this diff and remains a Stage 5 evidence-honesty dependency.
- `FleetJobScheduler.jobs` is an unbounded in-memory `Map` (no eviction/retention) and `POST /hub/fleet/jobs` has no rate limit; a job flood is bounded only by process memory. Not a regression in this diff, but it becomes remotely reachable now that a submit endpoint exists.
- The 6 skipped full-suite tests were not individually enumerated; they are pre-existing and unrelated to this diff.

## Gate

**FAIL (REVISE/BLOCK)**

Rationale: a P0 security defect and a P1 requirement deviation are present, so per the SOP §5 Stop-Work matrix ("Non-zero P0, P1, or P2 finding → Blocker") Gate 2 is not granted. The core endpoint mechanics are otherwise sound — session/CSRF admission, method guards, query-string ban, wildcard/empty-target rejection, idempotent execution, complete results accounting, and `fleet.job.create`/`complete`/`abort` emission all behave as specified, and `npm run check` (562/556/0/6), `check-public-tree`, and `git diff --check` all pass. The blocking items are the audit read surface disclosing live session IDs (P0), unscrubbed/cross-operator payload exposure (P1), and three P2 correctness/contract issues in `queryAudit` error handling, cancel-on-terminal response, and duplicate create auditing. Re-review is required after remediation.
