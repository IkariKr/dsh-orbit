In the Round 2 review (on commit `6a7137e`), Gate 3 was blocked with a **FAIL** verdict due to finding **P1-01 (NEW)**:

When `ScheduledWorkflowEngine.initTables()` creates `fleet_schedules`, `fleet_schedule_runs`, and their accompanying indexes on a persistent SQLite file, subsequent calls to `openRegistryDatabase(path)` upon Hub restart fail during `validateRegistrySchema()` because `validateSchemaVersion()` and `indexDefinitions()` query `sqlite_master` without scoping out engine-managed `fleet_%` tables and indexes.

2. `test/v08-stage4-resilience-security.test.mjs` was augmented with an end-to-end persistent database lifecycle test exercising initial hub launch, schedule creation, clean shutdown, and reopening with `openRegistryDatabase(dbPath)` on a restarted hub.

## 2. Detailed Audit of Round 2 Remediation (P1-01)

### 2.1 [P1-01] Persistent database schema contamination breaks Hub restart lifecycle — RESOLVED

- **Prior Defect**:
  When a Hub operates against persistent storage (a disk-backed SQLite database), `ScheduledWorkflowEngine` executes `initTables()` which runs:
  ```sql
  CREATE TABLE IF NOT EXISTS fleet_schedules (...);
  CREATE TABLE IF NOT EXISTS fleet_schedule_runs (...);
  CREATE INDEX IF NOT EXISTS idx_schedules_next_run ON fleet_schedules(next_run_at) WHERE status = 'active';
  CREATE INDEX IF NOT EXISTS idx_schedule_runs_schedule ON fleet_schedule_runs(schedule_id, triggered_at DESC);
  ```
  On subsequent Hub restarts, `openRegistryDatabase(path)` invokes `validateRegistrySchema(db)` -> `validateSchemaVersion(db, version)`.
  Prior to commit `3245014`, `validateSchemaVersion` executed:
  ```sql
  SELECT name FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%' ORDER BY name
  ```
  and `indexDefinitions` executed:
  ```sql
  SELECT name, tbl_name FROM sqlite_master WHERE type = 'index' AND name NOT LIKE 'sqlite_%' ORDER BY name
  ```
  Because `fleet_schedules` and `fleet_schedule_runs` were present, `actualTables` diverged from `expectedTables` (`expectedTableNamesFor(version)`), throwing `RegistryDatabaseError: malformed-schema: registry database tables do not match the supported schema for version 5`. Hub restarts on persistent databases were completely broken.

- **Remediation in `src/registry/sqlite.mjs`**:
  Lines 232-234:
  ```javascript
  function indexDefinitions(db) {
    const definitions = {};
    const indexes = db
      .prepare("SELECT name, tbl_name FROM sqlite_master WHERE type = 'index' AND name NOT LIKE 'sqlite_%' AND tbl_name NOT LIKE 'fleet_%' ORDER BY name")
      .all();
  ```
  Lines 434-438:
  ```javascript
  function validateSchemaVersion(db, version) {
    const expectedTables = expectedTableNamesFor(version);
    const actualTables = db
      .prepare("SELECT name FROM sqlite_master WHERE type = 'table' AND name NOT LIKE 'sqlite_%' AND name NOT LIKE 'fleet_%' ORDER BY name")
      .all()
      .map((row) => row.name);
  ```

- **Adversarial Assessment of Remediation**:
  1. **Strict Target Scoping**: In `indexDefinitions`, the filter `tbl_name NOT LIKE 'fleet_%'` specifically matches the target table of the index. This ensures that any rogue or unapproved index targeting a core Registry table (such as `nodes`, `reports`, or `audit`) will still be caught and rejected, while legitimate engine indexes on `fleet_schedules` and `fleet_schedule_runs` are properly ignored.
  2. **Core Table Protection**: In `validateSchemaVersion`, the filter `name NOT LIKE 'fleet_%'` only excludes tables namespaced with `fleet_`. Any non-fleet unexpected tables will still trigger an immediate `malformed-schema` error.
  3. **Database Integrity and Foreign Key Checks**: `checkRegistryIntegrity(db)` in `src/registry/sqlite.mjs` executes `PRAGMA integrity_check` and `PRAGMA foreign_key_check` across the entire database, ensuring database-wide integrity and relational consistency (including `REFERENCES fleet_schedules(schedule_id) ON DELETE CASCADE`) remain strictly validated before and after migrations.

- **Test Verification in `test/v08-stage4-resilience-security.test.mjs`**:
  Lines 443-488 test persistent database lifecycle: Hub server start, schedule creation, clean shutdown, and restart with `openRegistryDatabase` maintaining schema integrity and schedule state.
