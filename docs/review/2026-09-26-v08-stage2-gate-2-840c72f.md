### 2.3 Detailed Invariant & Code Correctness Verification

#### A. Session Authentication & CSRF Protection
- **Session Authentication**: Handled centrally in `src/registry/server.mjs` at line 700 via `validateSessionOnly(request, principal)`. Unauthenticated requests or expired sessions reject fail-closed with `HTTP 401 Unauthorized` (`no-session`). Mismatched injected principals reject with `HTTP 403 Forbidden` (`principal-mismatch`).
- **CSRF Token Validation**: Enforced at line 843 via `requireCsrf(request, session)` for all state-changing HTTP methods (`POST`, `DELETE`). Missing or invalid `x-csrf-token` headers reject with `HTTP 403 Forbidden` (`csrf-denied`).
- **Operator Attribution**: Schedule creation attributes `createdBy` strictly to `session.operatorPrincipal`, completely ignoring any caller-supplied `createdBy` field in the request body to prevent operator impersonation.

#### B. Bare Wildcard Rejection & Target Scoping
- In `POST /hub/fleet/schedules`, `targetSpec` is validated through `scheduleEngine.validateTarget(targetSpec)`:
  - Bare string wildcard (`"*"`) or objects declaring `{ mode: "all" }`, `{ mode: "broadcast" }`, or `{ nodeIds: "*" }` fail closed immediately with `HTTP 400 Bad Request` and structured error code `wildcard-prohibited`.
  - Explicit mode requires a non-empty array of node IDs (`empty-target-set`).
  - Capability mode requires a non-empty capability string (`invalid-capability-spec`).

#### C. Bounds & Interval Validation
- Cron expressions are validated via `parseCronExpression(cronExpression)`. Out-of-bounds fields (e.g. `60 * * * *`, `* 25 * * *`) return `HTTP 400 Bad Request` (`invalid-cron-bounds`). Invalid step values or non-numeric tokens return `HTTP 400` (`invalid-cron-step` / `invalid-cron-number`).
- Interval schedules require `intervalMs` to be an integer >= 1000. Values below 1000ms or non-integer inputs return `HTTP 400 Bad Request` (`invalid-interval`).

#### D. Safe URL Decoding (`safeDecodeUri`)
- All parametric routes matching `:id` (`/hub/fleet/schedules/:id`, `/hub/fleet/schedules/:id/runs`, `/hub/fleet/schedules/:id/pause`, `/hub/fleet/schedules/:id/resume`, `/hub/fleet/schedules/:id/trigger`, and `DELETE /hub/fleet/schedules/:id`) use `safeDecodeUri(rawScheduleId)`.
- Malformed percent-encoded sequences (such as `%ff` or truncated `%E0%A4%A`) safely return `HTTP 400 Bad Request` (`bad-request`) rather than throwing unhandled `URIError` exceptions.

#### E. Resource Existence & 404 Handling
- Each schedule endpoint verifies existence via `scheduleEngine.getSchedule(scheduleId)`.
- Non-existent schedules consistently return `HTTP 404 Not Found` with structured error code `not-found`.

#### F. State Transitions & 409 Conflict Handling
- `POST /hub/fleet/schedules/:id/pause`: Calling pause on a non-active schedule (already paused, completed, or error) safely rejects with `HTTP 409 Conflict` and error code `schedule-not-active`.
- `POST /hub/fleet/schedules/:id/resume`: Calling resume on a non-paused schedule (already active, completed, or error) safely rejects with `HTTP 409 Conflict` and error code `schedule-not-paused`.

#### G. Lifecycle Binding & Shutdown Cleanup
- Hub server creation (`createHubServer`) automatically instantiates `ScheduledWorkflowEngine` when a valid SQLite database handle is present.
- The engine instance is exposed on `server.scheduleEngine` and returned in the server handle object.
- The server `close` event handler binds cleanup: `scheduleEngine?.stop()` is invoked when the Hub terminates, ensuring any active timer handles are cleared.

#### H. Audit Trail & Credential Scrubbing
- All schedule mutations record structured audit logs in `registry.recordAudit`:
  - `fleet.schedule.create`: records `scheduleId`, `name`, `scheduleType`, `targetSpec`, and `nextRunAt`. The job payload is omitted from the audit log, preventing credential leakage in audit tables.
  - `fleet.schedule.pause`: records `{ scheduleId }`.
  - `fleet.schedule.resume`: records `{ scheduleId }`.
  - `fleet.schedule.trigger`: records `{ scheduleId, runId, jobId }`.
  - `fleet.schedule.delete`: records `{ scheduleId }`.
  - `fleet.schedule.dispatch`: recorded by the engine callback with actor `"system:scheduler"` and `{ scheduleId, runId, jobId, triggerType }`.

## 3. Findings

### [P3] Unused `SCHEDULE_ID_PATTERN` constant and lack of client-supplied `scheduleId` format validation

- **Location**: `src/registry/schedule-engine.mjs:9`, `src/registry/schedule-engine.mjs:324`
- **Description**:
  `src/registry/schedule-engine.mjs` defines:
  ```javascript
  const SCHEDULE_ID_PATTERN = /^sched_[0-9a-f]{16,64}$/;
  ```
  However, this regular expression is never referenced anywhere in `schedule-engine.mjs` or `server.mjs`.
  When a client provides a custom `scheduleId` in `POST /hub/fleet/schedules`, `createSchedule` accepts it directly (`id = scheduleId || randomScheduleId()`) without verifying that it matches `SCHEDULE_ID_PATTERN`.
- **Impact**: Low. If an operator passes an arbitrary string format (e.g. `my-schedule`), it is inserted into SQLite. If a duplicate ID is passed, SQLite raises a `UNIQUE constraint failed` error, which returns HTTP 400. However, enforcing `SCHEDULE_ID_PATTERN.test(id)` upfront (analogous to `JOB_ID_PATTERN` in `FleetJobScheduler`) would prevent malformed IDs and provide a clear, structured `invalid-schedule-id` error code.
- **Recommended Action**: In Stage 4 hardening, validate `if (scheduleId !== null && !SCHEDULE_ID_PATTERN.test(scheduleId))` in `createSchedule`.

### [P3] Negative integration test coverage gaps in `test/v08-stage2-schedule-endpoints.test.mjs`

- **Location**: `test/v08-stage2-schedule-endpoints.test.mjs`
- **Description**:
  While the implementation in `server.mjs` correctly handles:
  1. CSRF denial on schedule mutations (HTTP 403 `csrf-denied`),
  2. Missing session authentication (HTTP 401 `no-session`),
  3. Pausing an already paused schedule (HTTP 409 `schedule-not-active`),
  4. Resuming an already active schedule (HTTP 409 `schedule-not-paused`),
  5. Malformed URL decoding (HTTP 400 `bad-request`), and
  6. Audit query checks for pause, resume, delete, and dispatch actions;
  the integration test file `test/v08-stage2-schedule-endpoints.test.mjs` only tests the happy path lifecycle and two input validation errors (`wildcard-prohibited` and `invalid-cron-bounds`). The header comment in `test/v08-stage2-schedule-endpoints.test.mjs` explicitly mentions `7. CSRF and session authentication enforcement across all schedule mutation routes`, but no assertions actually omit or forge the CSRF token.
- **Impact**: Low. Verified independently via harness execution that the server implementation enforces all invariants. However, adding negative assertions directly into the permanent test file will guard against future regressions.
- **Recommended Action**: Add test assertions covering CSRF rejection, 409 state conflicts, and malformed URL decoding to `test/v08-stage2-schedule-endpoints.test.mjs` in Stage 4.

### [P3] `ScheduledWorkflowEngine.start()` background loop is not auto-started on Hub boot

- **Location**: `src/registry/server.mjs:1292-1306`, `bin/dsh-orbit-hub.mjs:142`
- **Description**:
  In `createHubServer`, `scheduleEngine` is instantiated and its shutdown cleanup (`scheduleEngine?.stop()`) is registered on server `close`. However, `scheduleEngine.start()` is not invoked within `createHubServer` or `bin/dsh-orbit-hub.mjs`.
  As a consequence, the engine's periodic timer loop (`evaluateDueSchedules`) and startup reconciliation (`reconcileOnStartup`) remain inactive unless the caller explicitly invokes `server.scheduleEngine.start()`.
- **Impact**: Expected for Stage 2 / low. Stage 2 specifically covers the REST management endpoints, manual trigger dispatches, and audit logs. Autonomous time-based execution is tested under Field 31 (`scheduledWorkflowAutomatedDispatch`) in Stage 4/5. Calling `start()` unconditionally inside `createHubServer` could also keep the Node.js event loop active in ephemeral test harnesses unless `timer.unref()` or an explicit opt-in option is provided.
- **Recommended Action**: In Stage 4 (Resilience & Concurrency), introduce a configurable `autoStartScheduleEngine: true` option in `createHubServer` and invoke `server.scheduleEngine?.start()` in `bin/dsh-orbit-hub.mjs`.
