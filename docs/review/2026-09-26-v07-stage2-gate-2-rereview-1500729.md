## Findings

### [P2] Credential scrubbing is key-based/heuristic and still leaks realistic token forms (RFC-0014 D5 not fully met)

`src/registry/fleet-scheduler.mjs:59-100` (`scrubSensitiveCredentials`), `src/registry/fleet-scheduler.mjs:339-357` (`getJob`)

The P1 remediation redacts credentials only when they sit under a credential-named key (`apiKey`, `password`, `secret`, `token`, `privateKey`, `authorization`, `cookie`, `set-cookie`) or when a string value matches one of three patterns (PEM private key, `Bearer <token>`, `dsh-orbit-hub-session=<value>`). RFC-0014 D5 requires "task payloads and output logs scrub tokens, private keys, and session cookies". Two realistic forms survive and are returned to every authenticated operator (job visibility is still not operator-scoped):

1. **Bare / inline tokens in output logs.** A node `stdout`/`stderr` line such as `API_TOKEN=abc123` is not matched (only `Bearer ...` is). Reproduced end-to-end (two operators, HTTP surface): operator-bob reads operator-alice's job detail and receives

   ```
   bob sees payload: {"envLine":"API_TOKEN=<sample-abc123def>","url":"postgres://user:pw@host/db","sessionId":"sess_abcdef0123456789abcdef0123456789","note":"password=<sample-password>"}
   bob sees stdout: "starting\nAPI_TOKEN=<sample-abc123def>\nconnect postgres://u:pw@h\n"
   bob sees stderr: "token=zzz999"
   ```

   This is the canonical place a token leaks (a `command` task dumping env/config/curl output). `getJob` is also the source for `listJobs`, `onJobCompleted`, and the GET detail/list routes, so the leak reaches every read path.

2. **The Hub's own session identifier.** `scrubSensitiveCredentials({sessionId:"sess_..."})` returns the value verbatim (`session_id` likewise), and the scrubber's key list does not include `key`, `auth`, `credential`, or `x-api-key` — all of which `sanitizeAuditDetail` in `registry.mjs` does catch. Verified: `{key:"K",auth:"A",x-api-key:"X",credential:"C"}` all pass through unredacted.

Impact: cross-operator credential disclosure, a direct deviation from RFC-0014 D5. It is graded P2 (not P1) because the structured key-based vectors and the three RFC-named classes in their canonical forms are handled, so the residual requires a credential embedded as a bare substring or under a non-enumerated key. Under the SOP §5 rule ("Non-zero P0, P1, or P2 finding → Blocker") it still blocks the Gate.

Minimal fix direction: align the key predicate with `sanitizeAuditDetail` (substring match on `session`, `token`, `secret`, `key`, `password`, `cookie`, `csrf`, `auth`), and redact inline `(?i)(token|secret|password|api[_-]?key|authorization|bearer)\s*[:=]\s*\S+` and bare `sess_[0-9a-f]+` occurrences inside string values.

### [P3] `sanitizeAuditDetail` does not recurse into arrays, so credential keys inside array elements leak

`src/registry/registry.mjs:75` (`} else if (v && typeof v === "object" && !Array.isArray(v)) {`)

The recursive redaction explicitly skips arrays: an array value is copied through unchanged. Verified: an audit detail `{items:[{token:"LEAK-TOKEN"},{secret:"LEAK-SECRET"}], nested:{arr:[{password:"LEAK-PW"}]}}` is returned by `POST /hub/audit/query` with every secret intact:

```
array detail: {"items":[{"token":"LEAK-TOKEN"},{"secret":"LEAK-SECRET"}],"nested":{"arr":[{"password":"LEAK-PW"}]}}
```

Graded P3 because no current audit action records an array of objects containing a credential key (all live `recordAudit` details are flat objects; capability `previous`/`next` are TEXT strings, not arrays), so there is no live trigger today — it is a latent hole in the very function the P0 fix introduced. Minimal fix: recurse arrays element-wise instead of passing them through.

### [P3] `sanitizeAuditDetail` over-redacts benign identifiers, degrading the audit read model

`src/registry/registry.mjs:64-74`

The key predicate is a substring `includes("key")` / `includes("auth")` match, so legitimate, non-secret audit fields are replaced with `[REDACTED]`. Verified: `{monkey:"monkey", hockey:"hockey"}` → both `[REDACTED]`, and the same rule redacts `keyId`/`tokenId`, which appear in real audit details (`hub.route-keys.rotate` → `currentKeyId`/`newKeyId`; `node.enrolled`/`node.paired` → `keyId`/`tokenId`; `hub.route-keys.provision` → `keyId`). The raw rows remain in SQLite (`detail_json` is untouched), so forensic completeness is preserved at the DB level and no consumer/test depends on these fields (full suite passes); impact is limited to the read-model usefulness of `GET /hub/audit` and `POST /hub/audit/query`. Minimal fix: narrow the predicate to whole-word/credential-suffix keys (e.g. exact `key`, or `secret`/`password`/`token`/`csrf`/`session` substrings) rather than any `key`/`auth` substring.

### [P3] Pre-existing never-5xx violation remains on non-fleet management routes

`src/registry/server.mjs:733`, `src/registry/server.mjs:747`

The new fleet routes correctly guard `decodeURIComponent` via `safeDecodeUri` and return 400 on malformed encoding (verified: `GET /hub/fleet/jobs/%ZZ` → 400, `GET /hub/fleet/jobs/%ZZ/audit` → 400, `POST /hub/fleet/jobs/%ZZ/cancel` → 400). However the same listener still returns `500 internal-error` for `GET /hub/nodes/%ZZ` and `GET /hub/nodes/%ZZ/route-target`, contradicting the transport's own stated invariant (`server.mjs:4` "5xx-never-allowed"; RFC-0007 security matrix "5xx upstream | failed case (never allowed)"). This class is pre-existing and not introduced by this diff, so it is P3 and does not block on its own; noted because Stage 2 touched this dispatcher and the invariant remains violated. Minimal fix: apply the same guarded decode to the node routes.

## Residual Risks

- **Audit-write failures remain silently swallowed and non-transactional (prior P3, unchanged).** `fleet-scheduler.mjs:555-557` (`try { this.onJobCompleted?.(...) } catch {}`) and `server.mjs:1074-1086` (the `fleet.job.complete` callback) still discard any error, and `fleet.job.create` is written after execution has already started asynchronously. RFC-0014 D5 ("Every fleet job execution writes directly to the Hub's authoritative SQLite audit table") can therefore fail unobservably for M28 field 8. Fail-safe, not corrupting.
- **`getJob(jobId, {scrub:false})` is an escape hatch that returns raw payload/results.** No caller currently uses it (verified by grep), but any future caller bypasses all scrubbing.
- **Cross-operator job visibility is still unrestricted.** The remediation chose scrubbing over operator scoping, so any authenticated operator can enumerate and read any other operator's job snapshot (and a replay of another operator's `jobId` returns that job's snapshot with 200). With Finding 1's gaps, this is the channel by which unredacted values are exposed. Whether cross-operator visibility is intended is not stated in RFC-0014 or the SOP; the multi-operator model is implied by RFC-0007 and the test suite's distinct `operator-alice`/`operator-bob` principals.
- **Underlying "session cookie value == session ID, no principal rebinding at the registry layer" design persists.** The new `validateSessionOnly` principal check is applied only when `operatorPrincipal.mode === "inject"`; the durable defense now exists at the transport, but `registry.validateSession` itself still resolves purely by `session_id`, so any future surface that discloses a session ID would still be exploitable.
- **`FleetJobScheduler.jobs` is an unbounded in-memory `Map`** with no eviction/retention and no submit rate limit; a job flood is bounded only by process memory. Pre-existing, but now remotely reachable via `POST /hub/fleet/jobs`.
- The 6 skipped full-suite tests were enumerated and are pre-existing, environment-gated, and unrelated to this diff.
