## 3. Findings

### [P3] Foreign key reference in `fleet_schedule_runs.job_id` points to non-table `fleet_jobs(job_id)`

- **Location**: `docs/rfc/0015-scheduled-workflows-and-fleet-automation.md:97`
- **Description**:
  In D1's SQLite schema definition for `fleet_schedule_runs`:
  ```sql
  CREATE TABLE IF NOT EXISTS fleet_schedule_runs (
    run_id TEXT PRIMARY KEY,
    schedule_id TEXT NOT NULL REFERENCES fleet_schedules(schedule_id) ON DELETE CASCADE,
    job_id TEXT REFERENCES fleet_jobs(job_id),
    ...
  );
  ```
  In Orbit v0.7, fleet jobs are managed in-memory by `FleetJobScheduler` (`this.jobs = new Map()`, `src/registry/fleet-scheduler.mjs:274`) and recorded in the `audit` table; there is no `fleet_jobs` table in `src/registry/sqlite.mjs`. With `PRAGMA foreign_keys = ON;`, creating this table succeeds, but inserting any non-null `job_id` fails immediately with `no such table: main.fleet_jobs`.
- **Impact**: Non-blocking for Stage 0 architecture approval. When Stage 1 implements the schema migration in `src/registry/sqlite.mjs`, either:
  1. Remove `REFERENCES fleet_jobs(job_id)` so `job_id` is an unconstrained reference column (`job_id TEXT`), or
  2. Define and create a persistent `fleet_jobs` table as part of the v7 schema migration.
- **Recommended Action**: In Stage 1, define `job_id TEXT` without the foreign key constraint unless a `fleet_jobs` persistence table is also introduced.
